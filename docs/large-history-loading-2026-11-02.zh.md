# 大量对话导致刷新和重启卡顿：定位、修复与验证

本次改动使用桌面客户端和独立 Web 部署共用的读取路径；不迁移配置文件，不重写现有对话。

## 已确认的原因

1. `listProjectSessions({ limit: 5 })` 原先依次读取所有 JSONL 的标题、摘要，再排序、分页。旧版长记录没有完整尾部元数据快照时，需要扫描整份记录恢复标题。首页只显示五条，也要付出整个项目历史的读取成本。
2. `listWebProjects()` 为计算数量和最后活动时间，也调用无分页的会话读取。页面接着请求预览时，会重复上述操作。
3. Gateway 的历史列表通过 `ProjectRuntimeRegistry.resolve()` 初始化各项目的模型、路由、工具、插件与监听器。浏览侧栏不需要这些执行能力。
4. Web 服务初始化时主动预热全局搜索。独立 worker 虽然不阻塞主线程，仍会扫描工作区、读取历史和建立索引，与首屏请求争抢磁盘和 CPU。
5. Web 的项目预览按项目串行请求，项目多时会叠加延迟。

因此，工作区扫描和历史加载都有影响，不能只归因于某一种部署方式。

## 实现方式及兼容性

- 新增仅检查文件属性的会话目录扫描，最多同时进行 16 次文件属性读取；并发请求可共享正在进行的同目录扫描，完成后即移除，不设置会掩盖外部改动的 TTL。
- 排序后只读取足够填满当前页的有效摘要。损坏记录会跳过，分页偏移仍按有效会话计算；`limit: 0` 和未指定 limit 的完整列表语义保留。
- 标题摘要使用最多 512 项、8 MiB 的进程内缓存；单项超过 256 KiB 不缓存。每次请求重新检查修改时间、变更时间和大小；创建、删除、追加及保持大小和修改时间的编辑均有回归覆盖。缓存对象不会直接交给调用方修改。
- 项目数量按非空的主会话文件统计，不包含内部任务、子目录或符号链接。损坏但非空的记录保留在存储数量中，页面读取时跳过；不会为精确判断损坏记录而重新遍历所有正文。
- 保留旧版标题恢复逻辑、`.cwd` 标记及冲突项目目录的解析；测试确认原始文件内容不变。修正旧标题测试中的冒号文件名：它在 Windows 会变成 NTFS 数据流，不能作为普通文件被枚举。
- Gateway 浏览历史直接读取项目存储，仅在实际使用会话时初始化执行能力。
- 全局搜索在首次搜索时启动。代价是首次搜索可能需要索引准备；后续增量索引和监听机制保持原实现。
- Web 项目预览最多并发四个，保持最终项目排序、进度及快照版本处理。

## 边界

这次消除了首屏对全部会话正文的依赖。目录枚举、文件属性读取仍随会话数量增长；实际选中的旧版超长会话可能仍需恢复其元数据。单个超长会话的正文加载和首次搜索索引耗时不在上述 95% 结论范围内。没有进行 macOS/Linux 实机计时。
