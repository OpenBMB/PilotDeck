## 结论

本轮真实浏览器操作没有复现图片消息重复、上传未完成时文字先发出、图片预览延迟到回答完成才出现，以及普通多阶段回答的思考错序。

不能据此宣称所有消息流问题都已解决。低上下文、低输出上限的压力测试出现了压缩失败及模型重新生成先前正文。原始增量和持久化历史均包含该重复正文，因此不是同一个前端消息块被重复渲染。具体压缩失败原因尚未定位；也未在本轮完成“正在压缩 → 成功完成，期间刷新”的可视验收。

本次没有修改业务代码。

## 压缩压力测试的剩余问题与限制

L1 请求模型连续输出 160 行编号记录。在同一轮的第二次响应后触发自动压缩及 reactive 压缩：

- 自动压缩 `f10d2cc1-2d97-4d2e-998f-7b86514bbfbe`：`skipped`，无可摘要的历史。
- reactive 压缩 `96626832-c7c1-4aa8-ba4c-d297e34e446d`：运行约 11.36 秒后 `failed`，涉及 4 条消息。
- 后端随后执行 `emergency_head_truncate`。第三次模型响应重新从第 001 条开始；这段内容有新的响应块 ID，并存在于原始增量和 HTTP 历史中。
- 界面显示一次“Context compaction failed”，位于第二次响应之后、第三次响应之前。

这证明需要继续检查压缩失败后的上下文保留与续写行为，而不能在前端按正文相似度删掉重复内容。当前证据不足以判断这是 PR 引入还是已有行为，也不足以归因于具体供应商或输出预算。没有为得到通过结论而修改这些行为。

其他 C1–C8 合成记录轮次多次触发 `no_summarizable_live_turns` 和应急截断，不能将这些瞬时 skipped 事件当作成功摘要的验收。真实成功压缩中的状态原位替换、压缩中刷新，以及精确控制的历史先到/增量后到与旧开始事件重放，仍需补充专门验证。本轮未重新运行已有自动化测试；rebase 后此前执行的 580 项相关测试及构建/类型检查是独立证据，不计作本轮手工通过项。
