# HALO 场景报告：原版 PilotDeck vs 当前优化版

> **对比范围声明**：本文只对比两个版本——
>
> - **原版**：基线 `cfc4d177`（即本分支起点，与官方 upstream/main 相同）
> - **当前版**：本分支 HEAD（含 4 个提交，其中最后两个尚未 push）
>
> 本文**只描述当前代码里已经存在的行为**，未实现的计划一律不出现。所有描述均可在源码中对应到具体位置。

---

## 1. 基础概念（新手必读）

### 1.1 模型、provider、endpoint 是三层不同的东西

```text
模型（model）     →  你点的"菜"
provider（供应商）→  提供"菜单"的公司
endpoint（端点）  →  后厨的真实地址
```

发一条消息的实际链路：路由器选模型 → 通过某 provider 的 API → 请求最终打到一个真实网络地址（endpoint）。

关键：**模型名字不告诉你它物理上跑在哪**。两道不同的菜可能出自同一个后厨（同一供应商的两个模型连同一个 endpoint）；一家公司也可能用两个品牌名共用一个后厨。

### 1.2 原版 PilotDeck 的恢复架构

```text
请求
 └→ RouterRuntime（src/router/RouterRuntime.ts）
     ├─ fallback：静态清单，按场景查配置表，顺序固定，按"模型名字"切换
     ├─ transientRetry：瞬态错误重试，独立计数
     ├─ zeroUsageRetry：空响应重试，另一套独立计数
     └─ ModelRuntime（src/model/streaming/streamModel.ts）
         ├─ maxRetries 内部网络重试（外层看不见、管不着）
         │    └─ 附带能力：首字节后中断 → 纯文本断点续写（设计良好的好功能）
         └─ provider HTTP 请求

 另有：session 级 provider 失败计数器（很薄的熔断器雏形，且把所有错误都记成 provider 故障）
 UI：  一条"重连中"提示通道
 统计：只记最终成功那次 attempt 的 usage
```

先说句公道话：**原版不是设计得蠢，而是它的隐含假设在特定真实条件下会失守**：

- 静态清单假设"清单上的模型彼此独立"，但别名常共享同一 endpoint；
- 各层独立计数假设"每层管好自己就够"，但没有人管总数；
- 通用退避假设"等待时长我自己估"，但 429 响应里 provider 已经给出了精确答案。

### 1.3 当前优化版架构（HALO）

HALO = **Health-Aware Logic for Outage recovery**，位于 RouterRuntime 内的恢复协调层，通过配置开关 `router.recovery.enabled: true` 启用，**关闭时行为与原版完全一致**（这是用配置解析回归测试锁定的）。

```text
请求
 └→ RouterRuntime
     ├─ 健康记忆 ProviderHealthTracker（新增，跨请求、按故障域）
     ├─ 错误分类 classifyRecoverySignal（新增：service/credential/task/cancelled/unknown）
     ├─ 全链预算（新增：maxAttempts + deadlineMs 覆盖一切）
     ├─ 能力预过滤（新增）+ 动态候选排序（新增）
     ├─ 语义安全锁（强化：已输出内容禁止重放）
     ├─ attempt 账本事件（新增：每次真实 dispatch 可观测）
     └─ ModelRuntime
         ├─ 首字节前重试 → HALO 拒绝，由 RouterRuntime 统一管理
         └─ 纯文本断点续写 → 保留，消耗全链预算、受 deadline 约束
```

HALO 的定位边界：主模型选谁仍是 Agent A 的职责，计费公式属于 Agent B，成功判定属于 Agent D——HALO 只负责"失败之后怎么恢复"。

## 2. 五个场景：原版 vs 当前版

### 场景一：故障发生时，系统选错逃跑路线

> 合并"同一故障 endpoint 反复被撞"+"429 限流乱等"+"408/409 漏网"三个痛点。共同本质：**系统既看不清故障的范围，也听不懂故障的指令。**

#### 情境

你配置了 fallback 链 `A → B → C`。某天 A 请求失败。此刻系统要回答两个问题：**故障有多大？接下来往哪走？**

#### 原版行为（三个失守点）

**失守点 1：按名字换模型，不看物理故障范围。**

```text
A = providerX 的 gpt-4        ──┐
B = providerX 的 gpt-4-mini    ──┼── 同一个 endpoint（同一个后厨）
C = providerY 的 claude        ─── 独立 endpoint
```

providerX 服务器挂了，A 和 B **同时都是死的**。原版 fallback 只查静态清单："A 失败，下一个是 B"——从头到尾没问过 B 和 A 是否连的同一个地址。对 B 的调用注定失败：白等一次往返、白烧一次尝试预算（若清单是 A、B1、B2 全指向同一坏 endpoint，预算耗光都轮不到健康的 C）、还给挣扎中的服务器再添一拳。

"它们连同一个地址"这个信息不在配置文件里，只存在于各自的 endpoint URL 中——原版代码只读清单、不读 URL。

**失守点 2：不听 provider 的等待指令。**

429（限流）不是故障，是拒绝："人满了，等会儿再来"。响应里的标准字段 `Retry-After: 30` 是 provider 明说的等待时长。但原版让它被通用的 `maxDelayMs`（客户端自估退避的封顶值）截短：

```text
maxDelayMs = 1s，收到 429 + Retry-After: 30s
→ 等待 min(30s, 1s) = 1s → 重试 → 必然又 429
→ 连撞 30 次，每次吃闭门羹，30 次调用全部无效
```

本质：一个为防客户端失控设计的保险丝，被拿来修剪服务器的明确指令。

**失守点 3：错误分类有缝隙。**

HTTP 408/409 在底层是"可重试"，在服务故障判定里却没有条目——结果它们可以触发 fallback，却不计入 provider 健康统计，也不走同路重试。一个反复 408 的 endpoint（网关过载的典型表现）在健康记录上永远"清白"。

#### 当前版行为

一个决策流程取代三个失守点（对应 `classifyRecoverySignal` + `providerFailureDomain` + 主循环决策）：

```text
失败
→ 错误分类（五类）：
     service（429/5xx/408/409/超时/网络/TLS/代理/过载）
     credential（认证/欠费）
     task（参数/上下文溢出/模态/工具参数——不记 provider 的错）
     cancelled（取消——谁的错都不是，不计健康）
     unknown（保守退出，保留原始诊断）
→ 故障域识别：记在"脱敏后的真实 endpoint"名下
     （protocol + url.protocol + host + path，剥掉用户名/密码/查询参数/hash）
→ 决策（先检查可行性，再宣布动作）：
     ├─ 429：有真正独立的候选？→ 直接切，不等
     │       没有？→ 完整遵守 Retry-After（豁免于 maxDelayMs）
     │            等待会超过剩余 deadline？→ 立即退出，不开始注定来不及的重试
     ├─ service 类：有界同路重试，或切独立 endpoint
     ├─ credential：该 provider 进入屏蔽名单，不用同一凭据再撞
     ├─ task 类：交给原有压缩/容量恢复路径，不切模型
     └─ cancelled：直接传播
```

> 一句话：**原版切换"模型名字"，当前版切换"故障域"；原版用自己拍的退避值，当前版让 provider 指令有豁免权；原版检查跟在决策后，当前版先看清全局再行动。**

#### 本场景引入的外部方案

**gRPC 的 pushback 思想**（详见第 3 章介绍）→ 落地为"Retry-After 豁免于本地退避上限 + 等待前先算剩余 deadline"。

**Envoy 的 outlier detection 思想**（详见第 3 章）→ 落地为"故障域 = 实际连接的 endpoint，而非 provider 名字"。

#### 验证（已有测试锁定）

- 共享 endpoint 场景对照：原版 `A → B → C`（3 次 dispatch、1 次无效、180ms），当前版 `A → C`（2 次、0 次、80ms）；
- Retry-After 豁免测试：所有候选同域 429、`maxDelayMs=1ms`、Retry-After=30ms → 当前版等完整 30ms 后成功（截短逻辑存在则必失败）；
- 408/409 一致性测试：进入健康统计、允许有界重试/切换。

#### 当前版仍做不到的

- 所有候选都在同一坏域时，只能更快、更诚实地承认失败；
- 故障域按 endpoint 划分：同一 endpoint 下两个独立配额的 API Key 会被一起误屏蔽（429 场景误伤）——已在代码注释和文档中标记为已知限制；
- Retry-After 不总是提供或不总是准：有就用，没有退回常规退避。

### 场景二：恢复机制自己制造新故障

> 痛点：半开探测洪峰 + 探测资格泄漏。

#### 情境

某 endpoint 故障一阵后冷却期满，进入"半开"状态——允许试探性地发**少量**请求，探测它恢复没有。此时用户正在跑多任务工作流，10 个并发请求都把它作为主模型。

#### 原版行为

先补新手概念。熔断器（circuit breaker）是防对故障服务疯狂重试的标准机制：

```text
closed（闭合）→ 正常放行
   │ 连续失败达阈值
   ▼
open（打开）→ 直接拒绝，不再打向故障服务（冷却期）
   │ 冷却期满
   ▼
half-open（半开）→ 放行"少量"试探请求
   ├─ 成功 → 回到 closed
   └─ 失败 → 回到 open
```

原版的问题：

1. **没有半开并发保护**。10 个请求各自判断"冷却结束了，可以试了"，10 个探测同时打到刚恢复、还脆弱的服务上 → 服务再次被打挂，或 10 个任务同时报错。"恢复机制把小故障放大成大故障"的经典事故模式被自己复刻了一遍。
2. **探测资格可能泄漏**。没有统一释放路径时，调用方取消或提前关闭流，资格被占着不放——之后所有请求都拿不到资格，该 endpoint 等于被永久拉黑。

#### 当前版行为

`ProviderHealthTracker` 的 `tryAcquire`/`release` 实现了探测租约，且**主候选和 fallback 走同一套**（第三轮迭代补上了主候选这个缺口）：

- **每故障域同一时刻最多一个探测请求**（`halfOpenProbeInFlight` 标志原子占用）；拿不到租约的请求得到明确的 `provider_circuit_open` 错误并转向下一候选，而不是死等；
- **租约在 `finally` 中释放**：无论探测成功、失败、用户取消、还是消费方提前关闭流（生成器被 GC/return），探测位都不会卡死；
- **用户显式指定的模型不偷偷切换**：显式选择跳过"候选屏蔽"检查，但不破坏租约内部状态；
- 半开探测失败 → 回到 open，冷却期指数增长（30s 起，每次翻倍，封顶 5 分钟），不会被一次失败永久拉黑，也不会无限快速重试。

已验证：并发请求同时到达，只有一个能进入半开探测；探测被取消后，下一请求立即取得租约。

#### 本场景引入的外部方案

**Azure Circuit Breaker 模式**（详见第 3 章）→ 落地为"每域单探测租约 + 指数冷却"。Azure 的示例是普通请求-响应，没有"消费方中途关流"这个变数，所以我们额外加了 `finally` 释放适配流式场景。

**AWS Builders' Library 的 "Retries are selfish" 原则**（详见第 3 章）→ 单探测、有界重试、deadline 中止在途请求，全部是这条原则的落地。

#### 当前版仍做不到的

- 租约是进程内的：网关跑多进程时每进程各一个探测名额（PilotDeck 网关是单进程架构，当前无此需求）；
- 拿不到租约且有其他候选时先走别的，没有候选时以 `provider_circuit_open` 退出——排队的公平性依赖事件循环顺序，无显式保证。

### 场景三：统一预算，但不误伤好功能

> 合并"多层重试预算放大"+"流式续写误杀"两个痛点。它们是一对：原版同一个底层开关控制着一件坏事和一件好事。

#### 情境

先看坏事。用户配置"最多重试 2 次"，但原版重试计数散落多层：

```text
ModelRuntime 层：maxRetries 次内部网络重试（外层看不见）
RouterRuntime 层：transientRetry 一套计数 + zeroUsageRetry 又一套
fallback 层：每切一次模型，上面两套计数部分归零
```

实际 dispatch 数可被放大到 5–8 次：钱花在哪不知道（用户以为 2 次，实际 8 次），deadline 被各层等待暗中叠加耗光，且放大倍数在服务最脆弱时最大。

再看好事。PilotDeck 的 ModelRuntime 有个设计精良的功能——**流式断点续写**：模型已流式输出 500 字纯文本 → 网络中断 → 带着已收到的内容重连同一模型 → 从断点继续写 → 用户几乎无感知。关键安全约束：只在"已输出的是纯文本"时使用。

**问题：这两件事共用同一个开关 `maxRetries`**——它同时控制"首字节前的网络重试"（该被统一预算接管的坏事）和"首字节后的纯文本续写"（该保留的好事）。统一预算最直接的做法是 `maxRetries=0` 一刀切——预算确实统一了，续写也没了。（我们第一版确实这样踩过坑，第三轮修正。）

#### 当前版行为

**其一：显式 retry gate 取代一刀切开关**（`streamModel.ts` 新增 `allowRetry` 回调参数）：

```text
首字节前失败 → 底层内部重试被 HALO 拒绝（allowRetry 返回 false），
              统一由 RouterRuntime 管理 → 预算不再被隐形循环放大
首字节后中断（纯文本）→ 续写放行（allowRetry 仅对 reason="continuation" 返回 true），
              但每次续写消耗一次全链 attempt，且等待必须放得进剩余 deadline，
              续写产生独立的 attempt 起止事件（进账本）
```

**其二：全链预算覆盖一切**（`RouterRecoveryConfig`）：

```yaml
router:
  recovery:
    enabled: true          # 总开关，关闭时行为与原版完全一致
    maxAttempts: 6         # 覆盖所有 dispatch：主请求+同路重试+fallback+续写
    deadlineMs: 30000      # 覆盖整条链的墙钟预算，包括等待和执行中
```

预算耗尽或 deadline 到期时产生明确的 `recovery_budget_exhausted` 错误（不再无限兜圈）；deadline 还能**中止正在执行中的 provider 请求**（`timeoutMs` 传入底层），而不只是决定"要不要开始下一次"。

**其三：语义安全锁**（比预算更重要的红线，原版只有雏形、当前版强化并测试锁定）：

```text
无任何输出            → 允许透明 retry / fallback
已输出纯文本          → 禁止跨模型 fallback（避免两份重叠答案），允许同模型续写
已输出 thinking       → 禁止任何自动重放
已输出工具调用        → 禁止任何自动重放
```

判定标准是"已向消费方交付过 text/thinking/tool 事件"（`isContentEvent`）——一旦锁定，绝不用重复输出或重复工具副作用换"成功率"。

#### 本场景引入的外部方案

**gRPC 的 commit point（提交点）思想**（详见第 3 章）→ 落地为上面的语义安全锁：gRPC 规定透明重试只在调用"被提交"（服务端开始产生响应）之前安全；我们映射到 LLM：纯文本续写不改变已交付内容（安全的 continuation），thinking/工具调用一旦产生就是"已提交"。

**AWS 的重试预算思想**（详见第 3 章）→ 落地为全链 `maxAttempts` + `deadlineMs`，一个预算管所有层。

#### 验证

- 原有 `streamModelRetry.spec.ts` 全部通过（原架构续写能力完好，无回归）；
- 新增测试：HALO 下续写消耗全链 attempt（预算耗尽则不再续写）；
- 配置关闭时行为与原版一致的回归测试。

#### 当前版仍做不到的

- `maxAttempts` 只约束单个请求：进程里 20 个并发请求各自试 6 次的跨请求放大仍未抑制（已标记为下一步，未实现）；
- thinking 和工具调用中断不做续写（合法性验证复杂，明确不做）；
- 续写与一次性生成可能有细微风格差异——这是原架构就有的特性，当前版不改变它。

### 场景四：候选检查的尺子和排序的眼睛

> 痛点：不合格候选被放行浪费预算 + 好候选被排到后面。

#### 情境

fallback 候选列表里可能有：不支持工具调用的模型（当前任务带工具）、上下文装不下的模型、不支持 thinking 的模型（当前任务开了思考）、不支持 JSON Schema 的模型（当前任务要求结构化输出）。原版不检查这些——轮到谁就把完整请求发给谁，失败后才学乖。

#### 原版行为

静态顺序，逐个撞：候选不支持工具 → 发过去 → provider 报错 → 切下一个。每次"撞墙"消耗一次 dispatch 预算和一轮往返时间，而且这些失败**完全可以提前预知**——能力信息就在 ModelRuntime 的能力表里，原版只是没看。

#### 当前版行为

**调用前预过滤**（`supportsRequestCapabilities` + `supportsMediaRequirements`），检查六项：

```text
工具调用支持（request.tools 非空时）
流式支持（request.stream 时）
system prompt 支持
thinking 支持（注意：仅当 thinking.enabled 且 mode ≠ "off"——
             明确关闭思考的请求不会错杀不支持思考的候选）
JSON Schema 输出支持（request.outputSchema 时）
上下文容量（估算输入 + 请求输出上限 ≤ maxContextTokens）
输入模态（图片等）：原生支持者优先，不支持的进入"媒体降级"队列排后，
              而不是直接丢弃
```

**动态排序**（`rankRemainingAttempts`）：剩余候选不再按静态配置顺序，而按罚分升序：

```text
健康状态罚分：open 1000000（实际跳过） > half_open 20 > degraded 10 > healthy 0
共享故障域罚分：与刚失败的域相同 +100     ← 场景一"直接跳过 B"的实现
可靠性罚分：(1 - 成功率) × 4
延迟罚分：EWMA 延迟 / 10000
成本罚分：候选的输入 token 估算费用
```

两条设计纪律：

- **冷启动保护**：成功率用 Beta(2,2) 先验平滑（窗口内成功数 + 2)/(窗口数 + 4)——新记录 0 次样本时成功率为 50% 而非 0，**一两次失败不会把一个 provider 判成极差**；
- **窗口有限**：成功率窗口 20 条、健康记忆容量 128 个域、记录 TTL 15 分钟——记忆是"近期经验"不是"永久档案"，不会无限增长。

#### 本场景引入的外部方案

**Envoy 的低样本保护思想**（详见第 3 章）→ 落地为 Beta(2,2) 先验 + 有限窗口。Envoy 在样本量不足时禁用成功率剔除、只用固定阈值，防止两三次失败得出极端结论；我们的 Beta 先验是同一原则在数值上的实现。

**成本感知排序**的输入价格数据来自 PilotDeck 原有的 `modelPricing` 工具（非我们新增，且未修改 Agent B 的计费公式——HALO 只读价格表用于排序罚分）。

#### 验证

- `thinking: off` 请求不误杀不支持思考候选的回归测试；
- 共享故障域候选被降权的对照实验（场景一数据）。

#### 当前版仍做不到的

- 上下文估算目前只算消息正文 token，不含 system prompt、工具 schema、output schema（已知偏小，可能误放行）；
- 估算用 `countMessagesTokens` 近似，非精确 tokenizer；
- 输出上限下调发生在过滤之后（可能误拦截"调一下上限就能用"的候选）。

这三点是审计确认的已知限制，**当前未实现修复**。

### 场景五：恢复过程从黑箱变账本

> 痛点：恢复过程对评测（Agent D）不可见——失败 attempt 的费用不入账、跳过原因不留痕、成功只记最后一次。

#### 情境

评测要回答"这次恢复花了多少钱、几次尝试、为什么跳过候选 X"。原版统计只记最终成功那次 attempt 的 usage——**失败 attempt 消耗的 token 和费用没有累计**（流式中断的失败也可能已产生部分 token 费用）；候选为什么被跳过没有记录；谁在什么时候失败过不可追溯。

#### 原版行为

`pilotdeck_router_transient_retry` 之类的零散事件存在，但没有统一的"每次真实 provider dispatch"账本。一个续写 dispatch 在统计上是隐形的——它消耗了钱，但账上不存在。

#### 当前版行为

新增 `pilotdeck_router_attempt` 事件，每次真实 provider dispatch（包括主请求、同路重试、fallback、续写）都有 start 和 end 两个事件，字段：

```text
sessionId / turnId          会话与轮次
attempt                     全链 attempt 序号
provider / model            谁
failureDomain               故障域（脱敏身份）
phase: start | end
end 额外：latencyMs、errorCode、usage、finishReason
```

配套修复：

- **取消不吞**：已取消的请求在进入恢复循环前显式抛出 abort 错误（原版可能静默返回），且**不计为 provider 故障**；
- **terminal error 只发一次**：所有候选失败时错误只发一次（原路径可能重复发出，已用测试锁定）；
- **脱敏**：failureDomain 只含协议+主机+路径，密钥、查询参数、hash 均被剥除，原始 provider 错误保留在诊断字段不进事件流。

Agent D 现在可以直接从事件总线采集这些数据做恢复率、恢复时长、恢复费用的完整分析，**不需要修改自己的成功判定标准**（账本是数据供给，不是评判）。

#### 本场景引入的方案

这里没有借用单一外部工具，而是**学界的成本核算纪律**：RouteLLM、FrugalGPT 这类 LLM 路由研究（详见第 3 章）能宣称"降 85% 成本"，前提是每一次调用的费用被完整计入——包括失败的和被跳过的。失败 attempt 不入账，成本对比就是自欺。HALO 的账本事件为这类分析提供地基。

另一个动机来自 PilotDeck 自己的产品定位：官方 README 的发布 benchmark（7 个复杂任务：Sonnet 4.6 主模型 + MiniMax-M2.7 子模型得分 70.6、成本 $3.15，对照单智能体 69.1 分、$18.36）卖点是"保持质量、显著降低成本"。恢复层的账本不清会直接侵蚀这条卖点——故障期的重复调用、无效等待都是成本黑洞。

#### 当前版仍做不到的

- 事件已齐，但"全链累计费用汇总"（把所有 attempt 的费用加总成单个数字）还没做——现在有数据，没汇总报表；
- UI 提示与真实动作的一致性未改（复用 `retry_progress` 通道让提示说真话是后续工作，当前 UI 行为同原版）；
- 事件量增加的吞吐成本未做专门压测。

## 3. 引入的外部方案详解

> 集中回答"HALO 里哪些东西不是我们发明的"。每个来源讲清楚三件事：**它是干啥的、它本来解决什么问题、我们借它来这里起什么作用。**

### 3.1 gRPC retry 设计（已采纳）

**是什么**：gRPC 是 Google 开源的远程过程调用（RPC）框架——微服务之间互相调用的通信层，Google 内部所有服务间通信都基于它的内部版本，全球大量公司的基础设施在用。它不是库，是工业级的通信标准，其重试规范经过全球规模流量的验证。

**它本来解决的问题**：微服务架构下，一次用户请求要穿过几十个内部服务，任何一环超时/过载都会失败。gRPC 的 retry 规范回答"客户端什么时候可以安全重试、该等多久、什么时候必须停"。

**我们借了什么**（两个思想）：

1. **服务端 pushback 必须尊重**：gRPC 里服务端可以返回 pushback 信息（THROTTLED + 建议等待时间），客户端必须遵守它而不是用自己的退避覆盖。→ **在 HALO 里的作用**：429 的 `Retry-After` 豁免于本地 `maxDelayMs` 封顶——provider 说等 30 秒就等 30 秒，不再出现"1 秒撞一次连撞 30 次"。
2. **commit point（提交点）**：gRPC 规定透明重试只在服务端"提交"（开始产生响应）之前安全；一旦提交，重试必须由应用层显式决定，因为重试可能产生重复副作用。→ **在 HALO 里的作用**：映射为语义安全锁——已输出纯文本/thinking/工具事件 = "已提交"，禁止重放；纯文本续写因为不改变已交付内容，被归入安全的 continuation。

**没借的部分**：gRPC 的跨请求重试令牌桶（retry throttling）我们评估后**尚未实现**，属于下一步计划，当前代码里不存在。

### 3.2 Envoy outlier detection 思想（已采纳）

**是什么**：Envoy 是 CNCF（云原生计算基金会，Kubernetes 所在的基金会）旗下的开源高性能代理，是 Istio 服务网格的数据面，大量云厂商的 API 网关核心。outlier detection（离群检测）是它的被动健康检查机制：不主动探测后端，而是**从正常流量中统计**每个后端的失败情况，自动把"离群"（持续失败）的后端临时踢出负载均衡池，过一段时间再放回来试试。

**它本来解决的问题**：负载均衡器后面的后端列表里，某台机器坏了但还在列表里——请求继续轮到它、继续失败、用户继续受影响。主动健康检查（定期 ping）要额外流量且探测的是"探测请求"而非真实请求；Envoy 的方案是免费地从真实流量中学习。

**我们借了什么**（三个思想）：

1. **健康状态按真实 endpoint 聚合，而不是按服务名**：Envoy 按后端主机统计，两个服务名指向同一主机就共享健康状态。→ **在 HALO 里的作用**：故障域 = 协议 + 脱敏 endpoint。providerX 的 gpt-4 和 gpt-4-mini 连同一个地址 → 同一个故障域 → 一个失败，另一个立即降权。"按名字换模型"升级为"按物理后厨逃跑"。
2. **低样本不用成功率激进剔除**：Envoy 要求最少请求量（request_volume）才启用成功率剔除，样本不足时只用固定阈值。→ **在 HALO 里的作用**：成功率用 Beta(2,2) 先验平滑——新记录 0 样本时成功率 50% 而非 0%，一两次失败不会把 provider 判成极差。
3. **内存有界**：Envoy 的检测窗口是滚动的、有限的。→ **在 HALO 里的作用**：成功率窗口 20 条、健康记忆容量 128 域、TTL 15 分钟——记忆是"近期经验"不是"永久档案"。

**没借的部分**：Envoy 的"最大剔除比例"（不许把所有后端一起踢光）当前未实现——当前版所有候选被屏蔽时直接以 `provider_circuit_open` 退出，不进入"最早恢复候选"模式。

### 3.3 Azure Circuit Breaker 模式（已采纳）

**是什么**：Azure 架构中心是微软的云架构模式文档库，Circuit Breaker（熔断器）是其中被引用最多的模式之一。熔断器一词借自电气工程：家里电流异常时保险丝自动断开，防止烧毁电器——软件里的熔断器在检测到下游故障时自动停止调用，防止雪崩。

**它本来解决的问题**：分布式系统的级联故障——服务 B 挂了，服务 A 的请求全部超时堆积，线程/连接池被占满，A 也挂了，然后 C……熔断器让 A 在检测到 B 故障后"果断止损"，快速失败而不是陪着超时。

**我们借了什么**：

- **half-open 必须限单探测**：Azure 明确要求半开状态"限制并发请求数为 1"，探测失败回 open 且冷却延长。→ **在 HALO 里的作用**：`tryAcquire`/`release` 租约——每个故障域同一时刻最多一个探测请求，主候选和 fallback 统一走这套。服务刚恢复时不会被 10 个并发探测再打挂。
- **指数冷却**：30s 起每次翻倍封顶 5 分钟——既不永久拉黑，也不无限快速重试。

**我们加的部分**（Azure 没有的）：`finally` 释放。Azure 的示例是普通请求-响应模型；LLM 流式场景多了"消费方中途关闭流"这个变数（生成器提前 return/抛出），我们用 `finally` 块保证任何退出路径都释放租约。

### 3.4 AWS Builders' Library 的重试哲学（已采纳）

**是什么**：AWS Builders' Library 是亚马逊资深架构师公开的运维经验文章库，写的都是亚马逊踩过的坑。其中 *Timeouts, retries, and backoff with jitter* 一文的第一句话 "**Retries are selfish**"（重试是自私的）是分布式系统的著名格言。

**它本来解决的问题**：重试在你的视角是"自救"，但在系统视角是"给别人添堵"——下游已经在挣扎，你的每次重试都是额外负担；所有客户端同时重试就是重试风暴，把小故障放大成全面瘫痪。

**我们借了什么**：这条原则作为一个**审视所有恢复设计的尺子**，具体落地点：

- 每故障域单探测（场景二）；
- 全链 `maxAttempts` + `deadlineMs` 限制单请求放大（场景三）；
- deadline 中止**正在执行中**的请求，而不只是限制"开始下一次"；
- 故障域降权优先于反复重试（场景一）。

### 3.5 《The Tail at Scale》的 hedged request（评估后未采纳）

**是什么**：Google 2013 年的论文《The Tail at Scale》（尾延迟治理的奠基文献，作者是 Google Fellow Jeffrey Dean 等），研究"为什么 99 分位延迟比平均延迟差几个数量级、怎么治"。其中一招是 **hedged request（对冲请求）**：一个请求发出后如果超过高分位延迟还没回，就再向**另一台服务器**发一个相同的请求，谁先回用谁的，另一个取消。

**它本来解决的问题**：分布式系统里慢的机器拖累整体——对冲用"多花一份计算"买"不被最慢者拖住"。

**为什么不采纳**：LLM 请求**按 token 计费**——对冲 = 双倍费用；且两个来源的流式输出无法合并（先回来的写到一半变慢了怎么办？）。收益（尾延迟降低）覆盖不了成本（双倍账单）。这是明确的"评估过、不采纳"，不是"不知道"。

### 3.6 学界 LLM 路由研究：RouteLLM 与 FrugalGPT（只借纪律，不借方法）

**是什么**：两个代表性的 LLM 路由学术工作。**RouteLLM**（lm-sys，即做 Chatbot Arena 排行的团队）用人类偏好数据训练一个分类器，预测"这个请求用便宜模型能否达到贵模型的效果"，报告在保持约 95% 强模型性能时成本最多降约 85%。**FrugalGPT**（Stanford）研究预算约束下的模型级联：先用便宜模型，输出不合格再升级到贵模型。

**它们本来解决的问题**：同一个请求，什么时候用贵模型是浪费、什么时候用便宜模型是质量风险——用数据回答，而不是拍脑袋。

**为什么不直接采纳**：模型选择是 **Agent A 的职责**。HALO 塞进学习型路由就成了"第二套路由器"——与 A 的决策打架、职责越界。任务书也明确"简单方案先于复杂学习算法"。

**我们借了什么**（一条纪律）：它们的成本对比之所以可信，前提是**每一次调用的费用被完整计入**——包括失败的、被跳过的。这条纪律直接催生了 HALO 的 attempt 账本事件（场景五）：失败 attempt 不入账，成本对比就是自欺。

### 3.7 采纳状态总表

| 来源 | 思想 | 状态 | 在 HALO 里的作用 |
|---|---|---|---|
| gRPC retry | pushback（Retry-After）尊重 | **已采纳** | 429 等待不被本地退避截短 |
| gRPC retry | commit point | **已采纳** | 已输出内容禁止重放；纯文本允许续写 |
| Envoy outlier | 按 endpoint 聚合健康 | **已采纳** | 故障域识别，跳过同域候选 |
| Envoy outlier | 低样本保护 | **已采纳** | Beta(2,2) 先验，一两次失败不判死刑 |

| Azure Circuit Breaker | half-open 单探测 + 指数冷却 | **已采纳** | 每域单探测租约（主候选+fallback 统一） |

## 4. 实验数据

### 4.1 故障注入对照（共享 endpoint 场景）

方法：可控假 provider 适配器按固定脚本注入故障（endpoint 1 永远失败，endpoint 2 成功），两组相同故障脚本与预算，虚拟时钟避免真实等待。

| | 调用序列 | 总 dispatch | 无效调用 | 恢复耗时 |
|---|---|---|---|---|
| 原版 | A → B → C | 3 | 1（对 B） | 180ms |
| 当前版 | A → C | 2 | 0 | 80ms |

完整数据：`artifacts/halo/comparison.json`（对照结果）、`artifacts/halo/attempt-traces.jsonl`（逐 attempt 原始轨迹）。复现命令：`npm run build && node dist/scripts/halo-fault-experiment.mjs artifacts/halo`。

### 4.2 定向回归（当前 42/42 通过）

- Retry-After 豁免（截短逻辑存在则必失败）；
- 并发单探测；取消后租约立即可再取；
- 原有续写能力无回归；续写受全链预算约束；
- 408/409 分类一致；
- `thinking: off` 不误杀候选；取消不记 provider 故障；
- 所有候选失败时 terminal error 只发一次；
- 配置关闭时行为与原版一致。

### 4.3 完整回归

525 项 spec：500 通过、21 失败、3 取消、1 跳过。失败数与改造前基线**一致**（均为既有的 Windows 路径/环境变量/Git ownership 敏感用例），HALO 未引入回归。

### 4.4 无故障开销

正常请求**零额外 provider dispatch**——健康查询是内存操作不是网络请求，能力过滤是纯计算。这是采纳健康机制的红线：如果修复方式是"每次调用前先探测一次"，那是用新的浪费换旧的浪费。

## 5. 当前版仍未解决的事（诚实清单）

| 未解决项 | 状态 | 说明 |
|---|---|---|
| 同 endpoint 独立配额被误屏蔽 | 已知限制 | 故障域按 endpoint 划分，429 场景可能误伤独立配额的 Key |
| 跨请求重试令牌桶 | 未实现 | 单请求预算管不住进程级放大（20 并发 × 6 次 = 120 次） |
| 上下文估算不含 system/工具 schema | 已知限制 | 估算偏小可能误放行，发过去才溢出 |
| 输出上限先过滤后调整 | 已知限制 | 可能误拦截"调一下上限就能用"的候选 |
| 全链费用汇总报表 | 未实现 | 事件数据已有，汇总未做 |
| UI 提示与真实动作一致性 | 未实现 | 当前 UI 行为同原版 |
| thinking/工具调用中断续写 | 明确不做 | 合法性验证复杂 |
| 预测"答案质量失败" | 明确不做 | 无可靠验证器时不假装能预测 |
| 多进程租约互斥 | 明确不做 | 单进程架构无此需求 |

## 6. 总结

原版到当前版，一句话：

> **原版的恢复是一张"固定转诊名单"——按名字排队、各层各自为政地重试；当前版是一个"知道哪些医院正在停诊、听得懂院方指令、控制抢救总时间、还不中断已开始的手术"的调度员。**

分场景一句话：

1. **场景一**：从"按名字换模型"到"按故障域逃跑"，从"自己拍等待时长"到"provider 指令有豁免权"；
2. **场景二**：恢复机制自己不再制造新故障——每域单探测、租约必释放；
3. **场景三**：一个预算管所有层，但用 commit point 思想保住了原架构的续写能力，守住"已输出内容绝不重放"红线；
4. **场景四**：候选先验能力再排序，冷启动有保护，记忆有边界；
5. **场景五**：每次 dispatch 进账本，取消不背锅，错误脱敏。

以及一条贯穿的纪律：**HALO 是协调层，不是第二套路由器**——主模型选择属于 Agent A，计费属于 Agent B，成功判定属于 Agent D；外部方案只借思想不搬架构，学习型路由明确不碰。
