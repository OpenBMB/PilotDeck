# HALO 场景报告：原版 PilotDeck vs 最终优化版

> 本报告面向不熟悉 PilotDeck 恢复链路的读者。全文只做一种对比：**原版架构（基线 cfc4d177） vs 最终优化版（含三次迭代）**，中间版本的曲折不展开（只在必要处一句话说明动机）。
>
> 另一个重点：介绍最终版里**引入的业界与学界成熟方案**——它们来自哪、原本解决什么问题、我们借了哪个思想、哪些评估后没有采纳。

## 1. 基础概念（新手必读）

### 1.1 模型、provider、endpoint 是三层不同的东西

```text
模型（model）     →  你点的"菜"
provider（供应商）→  提供"菜单"的公司
endpoint（端点）  →  后厨的真实地址
```

发一条消息的实际链路：路由器选模型 → 通过某 provider 的 API → 请求打到真实的网络地址（endpoint）。

关键：**模型名字不告诉你它物理上跑在哪**。两道不同的菜可能出自同一个后厨（同一供应商的两个模型连同一个 endpoint）；一家公司也可能用两个品牌名共用一个后厨。

### 1.2 一次失败的请求会经过哪些层

PilotDeck 的恢复能力分散在四层，这是理解全部场景的地图：

```text
ModelRuntime 层    网络重试、流式断点续写（checkpoint/continuation）
RouterRuntime 层   fallback 切换模型、空响应重试、provider 健康状态 ← HALO 的家
AgentLoop 层       上下文压缩、图片移除、不完整工具调用清理
工具执行层         工具权限控制、副作用保护
```

### 1.3 原版 PilotDeck 恢复架构全景

```text
请求
 └→ RouterRuntime
     ├─ fallback 静态清单（按场景查配置表，顺序固定，按"模型名字"切换）
     ├─ transientRetry（瞬态错误重试，独立计数）
     ├─ zeroUsageRetry（空响应重试，又一套独立计数）
     └─ ModelRuntime
         ├─ maxRetries 网络重试（内部循环，外层看不见）
         │    └─ 首字节后中断 → 纯文本断点续写（设计良好的好功能）
         └─ provider HTTP 请求

 另有：session 级 provider 失败计数器（很薄的熔断器雏形）
 UI：  一条"重连中"提示通道
 统计：只记最终成功那次 attempt 的 usage
```

先说句公道话：**原版不是设计得蠢，而是它的隐含假设在特定真实条件下会失守**——

- 静态清单假设"清单上的模型彼此独立"，但别名常共享同一 endpoint；
- 各层独立计数假设"每层管好自己的重试就够了"，但没有人管总数；
- 通用退避假设"等待时间我自己估"，但 429 响应里 provider 已经给出了精确答案。

### 1.4 最终优化版（HALO）架构全景

```text
请求
 └→ RouterRuntime —— HALO 恢复协调层
     ├─ 健康记忆（跨请求、按脱敏 endpoint 的故障域、容量/TTL/冷却/半开单探测）
     ├─ 错误分类 → 恢复动作（等待 / 同路重试 / 切换 / 续写 / 停止，带原因）
     ├─ 能力预过滤（工具/流式/thinking/JSON Schema/上下文容量/模态）
     ├─ 全链预算（maxAttempts + deadlineMs 覆盖一切，包括续写和等待）
     ├─ 语义安全锁（已输出内容 → 禁止重放）
     ├─ attempt 账本事件（每次真实 dispatch 可观测）
     └─ ModelRuntime（显式 retry gate）
          ├─ 首字节前重试 → 由 HALO 统一管理（不再内部循环）
          └─ 纯文本断点续写 → 保留，但消耗全链预算、受 deadline 约束
```

注意 HALO 的定位：**协调层，不是第二套路由器**。主模型选谁仍是 Agent A 的职责，计费公式属于 Agent B，成功判定属于 Agent D——HALO 只负责"失败之后怎么恢复"。

## 2. 五个合并后的痛点场景

### 场景一：故障发生时，系统选错逃跑路线

> 合并原"同一故障 endpoint"+"429 限流"+"错误分类缝隙"三个痛点。它们的共同本质：**系统既看不清故障的范围，也听不懂故障的指令。**

#### 情境

你配置了 fallback 链 `A → B → C`。某天 A 请求失败。此刻系统要回答两个问题：**故障有多大？接下来往哪走？**

#### 原版的行为与三个失守点

**失守点 1：按名字换模型，不看物理故障范围。**

```text
A = providerX 的 gpt-4        ──┐
B = providerX 的 gpt-4-mini    ──┼── 同一个 endpoint（同一个后厨）
C = providerY 的 claude        ─── 独立 endpoint
```

providerX 的服务器挂了，A 和 B **同时都是死的**。但原版 fallback 只查静态清单："A 失败，下一个是 B"——从头到尾没问过 B 和 A 是否连的同一个地址。对 B 的调用注定失败：白等一次往返、白烧一次尝试预算（若清单是 A、B1、B2 全指向同一坏 endpoint，预算耗光都轮不到健康的 C）、还给挣扎中的服务器再添一拳。

"它们连同一个地址"这个信息不在配置文件里，只存在于各自的 endpoint URL 中——原版代码只读清单、不读 URL。

**失守点 2：不听 provider 的等待指令。**

429（限流）不是故障，是拒绝："人满了，等会儿再来"。响应里的标准字段 `Retry-After: 30` 是 provider 明说的等待时长——全场最了解自己限流规则的一方给出的精确答案。

但原版让这个指令被通用的 `maxDelayMs`（客户端自估退避的封顶值）截短：

```text
maxDelayMs = 1s，收到 429 + Retry-After: 30s
→ 等待 min(30s, 1s) = 1s → 重试 → 必然又 429
→ 又等 1s → 又撞 → 连撞 30 次，每次吃闭门羹
```

这 30 次调用全部无效：烧预算、总耗时可能比老实等 30 秒更久、还骚扰 provider。本质是"为防客户端失控设计的保险丝，被拿来修剪服务器的明确指令"。

**失守点 3：错误分类有缝隙，部分错误绕过健康记忆。**

HTTP 408（请求超时）/409（冲突）在底层分类里是"可重试"，在服务故障分类里却没有对应条目。结果它们落进缝隙：**可以触发 fallback，却不计入 provider 健康统计**。一个 endpoint 反复 408（网关过载的典型表现），fallback 会一次次切过去，但健康记录上它永远"清白"——故障域记忆对它完全失效。

#### 最终版的行为

一个决策流程取代三个失守点：

```text
失败
→ 错误分类（429 / 5xx / 超时 / 认证 / 上下文溢出 / 取消，408/409 已补齐）
→ 故障域识别：把失败记在"脱敏后的真实 endpoint"名下
     （保留协议+主机+端口，剥掉密钥和查询参数，不泄露秘密）
→ 决策（先检查可行性，再宣布动作）：
     ├─ 429：存在真正独立的候选？→ 直接切，不等
     │       没有？→ 完整遵守 Retry-After（豁免于 maxDelayMs）
     │                等待会超过剩余 deadline？→ 立即诚实退出，不开始注定来不及的重试
     ├─ 5xx/超时：有界同路重试，或切独立 endpoint
     ├─ 认证错误：不用同一凭据重复撞
     ├─ 上下文溢出：交给原有压缩恢复路径，不切模型
     └─ 用户取消：立即传播，不计为 provider 故障
```

一句话总结思维转变：

> **原版切换的是"模型名字"，最终版切换的是"故障域"；原版用自己拍的退避值，最终版让 provider 的指令拥有豁免权；原版的检查跟在决策后面，最终版先看清全局再行动。**

#### 借鉴来源

- **gRPC**（Google 开源的远程调用框架，Google 内部所有服务间通信的基础，其重试设计经全球规模验证）：它的 retry 规范要求客户端尊重服务端 pushback（对应 HTTP 的 Retry-After），且"重试决策必须考虑调用剩余 deadline"。→ 我们采纳了"Retry-After 豁免于本地退避上限"和"等待前先算 deadline 够不够"。
- **Envoy**（CNCF 旗下开源代理，Istio 服务网格的数据面，大量云厂商网关的核心）：它的 outlier detection（离群检测）按真实 endpoint 而非服务名聚合健康状态。→ 我们采纳了"故障域 = 实际连接的 endpoint"。

#### 边界

- 所有候选都在同一坏域时，最终版变不出活候选，只能更快、更诚实地承认失败；
- 故障域目前只按 endpoint 划分：同一 endpoint 下两个独立配额的 API Key 会被一起误屏蔽（429 场景误伤）。拆成"可用性域 / 配额域 / 凭据域"三层是下一步计划；
- Retry-After 不总是给或不总是准：有就用（最强证据），没有就退回常规退避，不假装能读懂没说的信息。

### 场景二：恢复机制自己制造新故障

> 原"探测洪峰"痛点。前一场景的故障域记忆解决"记住谁坏了"，本场景解决"别忘了它自己也会闯祸"。

#### 情境

某 endpoint 故障一阵后冷却期满，进入"半开"状态——允许试探性地发**少量**请求，探测它恢复没有。此时用户正在跑多任务工作流，10 个并发请求都把它作为主模型。

#### 原版的行为

先补一个新手概念。熔断器（circuit breaker）是防止对故障服务疯狂重试的标准机制，三个状态：

```text
closed（闭合）→ 正常放行
   │ 连续失败达阈值
   ▼
open（打开）→ 直接拒绝，不再打向故障服务（冷却期）
   │ 冷却期满
   ▼
half-open（半开）→ 放行"少量"试探请求
   ├─ 成功 → 回到 closed
   └─ 失败 → 回到 open
```

半开状态的核心约束是"**少量**"——对端可能刚缓过来、容量还很脆弱。原版的问题有两层：

1. **没有半开并发保护**。10 个请求各自独立判断"冷却结束了，可以试了"，10 个探测同时打到刚恢复的服务上 → 服务再次被打挂，或 10 个任务同时报错。"故障时所有客户端疯狂重试，把小故障放大成大故障"的经典事故模式，被恢复机制自己复刻了一遍。
2. **探测资格可能泄漏**。如果没有统一的释放路径，调用方取消、或提前关闭流式连接时，探测资格被占着不放——之后所有请求都拿不到资格，该 endpoint 等于被永久拉黑。

#### 最终版的行为

- **主候选和 fallback 走同一套租约机制**：同一时刻每个故障域最多一个探测请求，其余请求先选别的候选或等待；
- **租约在 `finally` 中释放**：无论探测成功、失败、用户取消、还是消费方提前关闭流，探测位都不会卡死。已验证：取消探测后，下一个请求能立即重新拿到租约；
- **明确指定模型的语义不变**：用户显式选定的模型不偷偷切换，显式选择可以绕过"跳过"，但不破坏内部租约状态。

#### 借鉴来源

- **Azure 架构中心 Circuit Breaker 模式**（微软架构模式文档库中被引用最多的模式之一）：明确要求 half-open 状态"限制并发请求数为 1"，并强调探测请求失败要回到 open 且冷却期延长。→ 我们的"每域单探测租约"就是它的直接落地，额外加了 `finally` 释放以适配流式场景（Azure 的示例是普通请求-响应，没有"消费方中途关流"这个变数）。
- **AWS Builders' Library**（亚马逊架构师写的运维经验文章库）有篇经典文章叫 *Timeouts, retries, and backoff with jitter*，第一句话是 "**Retries are selfish**"（重试是自私的）——你的每一次重试都在加重别人的负担，重试风暴是大故障的标准放大器。→ 这是"宁可少探测、不可洪峰"的原则出处。

#### 边界

- 租约是进程内的。网关跑多进程时每进程各一个探测名额（N 进程 = N 个探测）。跨进程互斥需要 Redis 之类外部存储，当前明确不做——PilotDeck 网关是单进程架构；
- 拿不到租约的请求若有其他候选会先走别的，没有候选则排队等租约；这个排队的公平性目前依赖事件循环顺序，没有显式保证。

### 场景三：统一预算，但不能误伤好功能

> 合并原"多层重试预算放大"+"流式续写误杀"两个痛点。它们是一对：同一个底层开关控制着一件坏事和一件好事，naive 的修复会一起关掉。

#### 情境

先看坏事。用户配置"最多重试 2 次"，但原版的重试计数散落在多层：

```text
ModelRuntime 层：maxRetries 次内部网络重试（外层看不见）
RouterRuntime 层：transientRetry 一套计数
                  zeroUsageRetry 又一套计数
fallback 层：每切一次模型，上面两套计数部分归零
```

实际 dispatch 数可被放大到 5–8 次：钱花在哪不知道（用户以为 2 次，实际 8 次），deadline 被各层等待时间暗中叠加耗光，且放大倍数在服务最脆弱时最大。

再看好事。PilotDeck 的 ModelRuntime 有一个设计精良的功能——流式断点续写：

```text
模型已流式输出 500 字纯文本 → 网络中断
→ ModelRuntime 记录已收到的内容（checkpoint）
→ 重连，把"已有的 500 字 + 续写指令"发回同一模型
→ 模型从断点继续写 → 用户几乎无感知
```

它的关键安全约束：只在"已输出的是纯文本"时使用——续写不改变已交付内容，只是接下去。

**问题在于：这两件事共用同一个开关。** `maxRetries` 同时控制"首字节前的网络重试"（该被统一预算接管的坏事）和"首字节后的纯文本续写"（该保留的好事）。统一预算最直接的做法是把 `maxRetries` 设为 0——一刀切之后预算确实统一了，续写也没了。我们第一版正是这样踩坑的：流式中断后的恢复被推到上层 AgentLoop，更慢、用户感知更明显（输出停了再重来）。**修复一个痛点引入另一个痛点。**

#### 最终版的行为

把"一刀切开关"改成**显式 retry gate**——两个独立判断：

```text
首字节前失败 → 底层不再内部重试，由 RouterRuntime 统一管理（预算不再放大）
首字节后中断（纯文本）→ 续写保留，但：
     · 每次续写消耗全链 attempt 预算
     · 续写等待必须放得进剩余 deadline
     · 续写产生独立的 attempt 起止事件（进账本，评测可见）
```

同时全链预算覆盖一切：底层重试、空响应重试、同路重试、fallback、续写，全部消耗同一个 `maxAttempts` 和 `deadlineMs`；deadline 能中止**正在执行中**的请求，而不只是决定"要不要开始下一次"。

还有一条比预算更重要的安全线（第一版就有、最终版继续锁定）——**已产生的内容类型决定允许的恢复动作**：

```text
无任何输出            → 允许透明 retry / fallback
已输出纯文本          → 禁止跨模型 fallback（避免两份重叠答案），允许同模型续写
已输出 thinking       → 禁止任何自动重放
已输出工具调用        → 禁止任何自动重放
工具已执行（有副作用）→ 只能由 AgentLoop 根据工具执行账本决定
```

#### 借鉴来源

- **gRPC 的"提交点"（commit point）思想**：gRPC 规范规定，透明重试只在调用"被提交"（服务端开始产生响应）之前安全；一旦提交，重试必须由应用层显式决定。这是分布式系统对"重放的语义安全边界"的经典答案。→ 我们把它映射到 LLM 场景：纯文本续写不改变已交付内容（相当于安全的 continuation），而 thinking、工具调用一旦产生就是"已提交"——重放会改变用户可见结果或产生重复副作用。
- **AWS Builders' Library 的"重试预算"（retry budget）**：单次调用的重试上限不够，还要限制重试占总流量的比例。→ 我们的全链 `maxAttempts`/`deadlineMs` 覆盖单请求；跨请求的全局令牌桶是下一步计划（见第 5 章）。

#### 边界

- 续写不是完美的：模型看到"已有文字+续写指令"的上下文，可能与一次性生成有细微风格差异。这是原架构就有的特性，最终版不改变它；
- thinking 和工具调用中断目前直接失败交给上层，不做续写——合法性验证复杂，明确不做；
- RouterRuntime 管"同一次模型调用的续写"，AgentLoop 管"跨调用的任务级恢复"（重新规划、重新执行工具），边界不重叠。

### 场景四：候选检查用错尺子（计划中，未实现）

> 原"候选过滤用错请求"痛点。**注意：本场景是下一步计划（P3），不在当前代码里。**

#### 情境与问题

fallback 候选过滤要判断"这个候选的上下文装不装得下当前请求"。但估算只算消息正文 token，漏掉了 system prompt、工具名称/描述/JSON Schema（工具多时可达数千 token）、output schema、thinking 预算、provider 序列化开销。两个方向的错都会犯：

```text
误放行：算出 30K"能放下"（按 32K 上限）
        实际含工具 schema 共 35K → 发过去上下文溢出 → 白花一次失败
        （fallback 到上下文更小的候选，恰恰容易在工具多的任务上出这事）

误拦截：候选 maxOutputTokens = 8K，过滤时按 8K 预留，判"装不下"
        但若先把输出上限调到 2K，其实装得下
        → 一个本来可用的候选被无声扔掉（上限调整发生在过滤之后，顺序错误）
```

#### 计划的修复（P3：PreparedAttempt）

为每个候选先构造**最终请求**再验证：构造最终请求 → 应用媒体降级和输出上限调整 → 算完整输入预算（system+消息+工具 schema+output schema+thinking）→ 验证能力与上下文 → 才进入排序。每个候选产出一份"预检报告"（最终请求、能力结果、完整估算、健康状态、预计延迟费用、不可执行原因），`maxFallbacks` 名额在去重和兼容处理后分配——避免无效配置占满名额、健康候选永远进不了链。

#### 借鉴来源

- **Envoy 的低样本保护**：outlier detection 在样本量不足时禁用成功率剔除，只用固定阈值——防止两三次失败就得出极端结论。→ 候选排序同样需要"样本少时保守"的原则。
- **学界 RouteLLM / FrugalGPT 的分工边界**（见第 3 章）：它们证明"每个候选的价值 = 能力适配 × 可用性 × 成本"可以显式计算，但学习型路由属于主模型选择（Agent A 的职责），HALO 只消费其成本目标做可解释的约束排序，第一版明确"简单方案先于复杂学习算法"。

### 场景五：黑箱恢复——用户看不见，评测算不清

> 合并原"UI 提示失真"+"账本不完整"两个痛点。共同本质：恢复过程是黑箱，对用户和评测都不透明。

#### 情境与问题

**对用户**：UI 有一条"重连中/正在切换模型…"提示通道，但恢复动作只有一种展示。rate limit 场景下文案和真实动作对不上：

```text
用户看到："正在切换模型…"（切换很快，预期马上有结果）
系统实际：在等 Retry-After 的 30 秒
实际体验：卡 30 秒没反馈 → 大概率手动取消 → 前功尽弃
```

提示不真实比没有提示更糟——它制造了错误的预期。

**对评测（Agent D）**：要回答"这次恢复花了多少钱、几次尝试、为什么跳过候选 X"，但统计只记最终成功那次 attempt 的 usage；**失败 attempt 消耗的 token 和费用没有累计**（流式中断的失败也可能已产生部分 token 费用）；候选被跳过没有原因记录；健康状态变化前后不可见。

#### 最终版已做的部分

- **continuation 的 dispatch 现在有独立的 attempt start/end 事件**（含 provider、模型、attempt 序号、故障域、错误类型、延迟、usage、停止原因）——续写不再隐形，评测能看到每次真实 provider 调用；
- **取消信号在进入恢复循环前显式抛出**，不静默吞掉；
- **所有候选失败时只发一次 terminal error**（原路径可能重复发出，已用测试锁定）。

#### 计划中的部分（P4 + P6）

UI 侧：复用现有 `retry_progress` 通道让提示说真话（不新增组件）：

```text
"服务要求等待 3 秒"（429 等待中）
"正在切换到备用服务"（真的在切）
"备用模型不支持当前工具，已跳过"（候选被过滤）
"剩余时间不足，已停止无效重试"（deadline 退出）
"连接中断，正在续写已有回答"（continuation）
"已收到部分内容，为避免重复输出，不切换模型"（语义锁定）
```

账本侧：全局 dispatch 序号、恢复动作及机器可读原因、健康状态 before/after、Retry-After 与实际等待、决策时剩余 deadline、候选跳过原因、单次与全链累计的 usage/费用/耗时。原始 provider 错误保留用于诊断，落盘前结构化脱敏。

#### 借鉴来源

- **学界的成本核算传统**：RouteLLM 和 FrugalGPT 之所以能宣称"降 85% 成本"或"预算内最大化质量"，前提是**每一次调用的费用被完整计入**——包括失败的和被跳过的。失败 attempt 不入账，成本对比就是自欺。HALO 的账本为 Agent A/B 的成本优化和 Agent D 的评测提供这个地基。
- **PilotDeck 自己的产品定位**：官方 README 的发布 benchmark（7 个复杂任务：Sonnet 4.6 主模型 + MiniMax-M2.7 子模型得分 70.6、成本 $3.15；对照单智能体 69.1 分、$18.36）卖点是"保持任务质量、显著降低成本"。恢复层的账本不清会直接侵蚀这条卖点——故障期的重复调用、无效等待、悄悄升级到昂贵模型，都是成本黑洞。

#### 边界

- 不修改 Agent D 的成功判定（账本是数据供给，不是评判）；
- 事件量增加有吞吐成本，需评估事件总线与落盘策略。

## 3. 我们从业界和学界引入了什么

集中回答"HALO 里哪些东西不是我们发明的"。每项标注采纳状态。

### 3.1 来源速览（新手向）

| 来源 | 是什么 | 它的战场 |
|---|---|---|
| **gRPC** | Google 开源 RPC 框架 | Google 内部及全球微服务间通信的事实标准之一 |
| **Envoy** | CNCF 开源代理 | Istio 服务网格数据面，大量云厂商网关核心 |
| **Azure 架构中心** | 微软架构模式文档库 | .NET/云生态的模式参考 |
| **AWS Builders' Library** | 亚马逊架构师经验文章库 | 全球最大电商的运维智慧 |
| **《The Tail at Scale》** | Google 2013 论文 | 尾延迟治理的奠基文献 |
| **RouteLLM**（学界，lm-sys） | LLM 路由研究 | 用偏好数据训练强弱模型选择 |
| **FrugalGPT**（学界，Stanford） | LLM 级联研究 | 预算约束下的模型链调用 |

这些来源的共同点：都在**真实大规模流量里被火烧过**，它们的重试/熔断/健康设计不是论文推演，是事故换来的。PilotDeck 面对的问题（多个 LLM provider、限流、断流、fallback）在结构上与它们面对的问题（多个后端、过载、超时、重试）同构——这是借鉴成立的理由。

### 3.2 已采纳（在当前代码里）

| 思想 | 来源 | 在 HALO 里的落地 | 对应场景 |
|---|---|---|---|
| 服务端 pushback（Retry-After）必须尊重，不被本地退避上限修剪 | gRPC retry 规范 | Retry-After 豁免于 `maxDelayMs`；等待前先算剩余 deadline | 场景一 |
| 健康状态按真实 endpoint 而非服务名聚合 | Envoy outlier detection | 故障域 = 协议 + 脱敏 endpoint，跨请求记忆 | 场景一 |
| 调用"提交"后停止透明重试 | gRPC commit point | 已输出纯文本/thinking/工具事件 → 禁止重放；纯文本允许安全续写 | 场景三 |
| half-open 限单探测 | Azure Circuit Breaker | 每故障域单探测租约（主候选+fallback 统一） | 场景二 |
| 重试是自私的，防重试风暴 | AWS Builders' Library | 单探测、全链预算、deadline 中止在途请求 | 场景二/三 |
| 指数退避 + 上限 | AWS / 通用实践 | 冷却期指数增长，但 Retry-After 豁免 | 场景一 |

### 3.3 计划采纳（明确排期，未实现）

| 思想 | 来源 | 计划 | 优先级 |
|---|---|---|---|
| 跨请求重试令牌桶（失败耗令牌、成功补令牌、不足则停） | gRPC retry throttling | 抑制进程级重试风暴：单请求 `maxAttempts` 管不住 20 个并发请求各试 5 次 | P1 |
| 错误分桶（本地网络错误 vs 上游故障 vs 配额 vs 凭据分开统计） | Envoy（local origin vs upstream） | 429 记配额域、认证记凭据域、5xx 记可用性域；用户取消不记任何域 | P2 |
| 低样本不用成功率激进剔除 | Envoy（request_volume 门槛） | 冷启动样本少时只用固定阈值 | P2（原则已部分遵循） |
| 最大剔除比例（不许把所有候选一起拉黑） | Envoy（max_ejection_percent） | 所有候选被屏蔽时进入受控的"最早恢复候选"模式而非死锁 | P2 |

### 3.4 评估后明确不采纳

| 方案 | 来源 | 不采纳的理由 |
|---|---|---|
| **Hedged request（对冲请求）**：一个请求慢了就并行发第二个，取先回来的 | 《The Tail at Scale》、gRPC hedging | LLM 请求按 token 计费，对冲 = **双倍费用**；且两个来源的流式输出无法合并。只在未来 shadow 实验显示用户尾延迟明显改善、且费用可控时才重新考虑 |
| **服务网格式外部健康检查层** | Envoy/Istio 全套 | PilotDeck 是单进程网关，引入独立 sidecar/控制面是杀鸡用牛刀，运维复杂度远超收益 |
| **学习型路由（预测哪个模型质量更高/更便宜）** | RouteLLM、FrugalGPT | 这是主模型选择（Agent A）的职责，HALO 塞进学习路由就越权成了第二套路由器；且任务书明确"简单方案先于复杂学习算法"，无可靠验证器时不预测答案质量 |
| **跨进程分布式熔断（Redis 共享状态）** | 通用分布式系统实践 | 当前单进程架构用不上；等真有多进程部署需求再评估 |

## 4. 实验数据对比

### 4.1 故障注入对照（共享 endpoint 场景）

方法：可控假 provider 适配器按固定脚本注入故障（endpoint 1 永远失败，endpoint 2 成功），两组使用相同故障脚本与预算，虚拟时钟避免真实等待。

| | 调用序列 | 总 dispatch | 无效调用 | 恢复耗时 |
|---|---|---|---|---|
| 原版 | A → B → C | 3 | 1（对 B） | 180ms |
| 最终版 | A → C | 2 | 0 | 80ms |

### 4.2 关键回归测试（当前 42/42 定向通过）

- **Retry-After 豁免**：所有候选同域 429、`maxDelayMs=1ms`、Retry-After=30ms → 断言等待完整 30ms 后重试成功（若截短逻辑存在则必失败）；
- **并发单探测**：并发请求同时到达，断言只有一个进入半开探测；
- **取消无泄漏**：探测被取消后，下一请求立即取得租约；
- **续写不回归**：原有 `streamModelRetry.spec.ts` 全部通过（原架构续写能力完好）；
- **续写受预算**：HALO 下 continuation 消耗全链 attempt（预算耗尽不再续写）；
- **408/409 一致**：进入健康统计、允许有界重试/切换；
- **次生误杀防护**：`thinking: off` 的请求不会错杀不支持思考的候选；
- **取消不污染**：已取消的请求不记 provider 故障；
- **单次 terminal error**：所有候选失败时错误只发一次。

### 4.3 完整回归

525 项 spec：500 通过、21 失败、3 取消、1 跳过。失败数与改造前基线一致（均为既有的 Windows 路径/环境变量/Git ownership 敏感用例），HALO 未引入回归。

### 4.4 无故障开销

正常请求**零额外 provider dispatch**——健康检查是内存查询不是网络请求，能力过滤是纯计算。这是采纳任何健康机制的红线：如果修复方式是"每次调用前先探测一次"，那是用新的浪费换旧的浪费。

## 5. 没有解决的事（诚实清单）

| 未解决项 | 状态 | 说明 |
|---|---|---|
| 故障域太粗：同 endpoint 独立配额被误屏蔽 | 计划 P2 | 拆可用性/配额/凭据三层身份 |
| 跨请求重试令牌桶 | 计划 P1 | 单请求预算管不住进程级放大 |
| 候选过滤不含 system/工具 schema token；输出上限先过滤后调整 | 计划 P3 | PreparedAttempt 预检报告 |
| UI 提示与真实动作对不上 | 计划 P4 | 复用 retry_progress 通道说真话 |
| 失败 attempt 费用未入总账（事件已有，汇总未做） | 计划 P6 | 完整恢复账本 |
| 多进程部署下租约每进程一份 | 不做 | 单进程架构，无需求 |
| 预测"答案质量失败" | 不做 | 无可靠验证器时不假装能预测 |
| 所有候选同坏域时提升恢复率 | 不可能 | 只能更快更诚实地失败 |

故障注入结论仅适用于文档所述故障分布，不构成线上故障率证明。探索目标（恢复时间降 25%、无效重试降 50%）在共享 endpoint 场景中已超预期达成（恢复时间 -56%、无效重试 -100%），但这是单一故障分布下的结果，不外推。

## 6. 总结

原版到最终版的转变，一句话版本：

> **原版的恢复是"一张固定转诊名单"——按名字排队，各自为政地重试；最终版是一个"知道哪些医院正在停诊、听得懂院方指令、控制抢救时间、还不中断手术"的调度员。**

分场景的一句话：

1. **场景一**：从"按名字换模型"到"按故障域逃跑"，从"自己拍等待时长"到"provider 指令有豁免权"；
2. **场景二**：恢复机制自己不再制造新故障——单探测、租约必释放；
3. **场景三**：预算统一覆盖一切，但用 commit point 思想保留了原架构的续写能力，并守住"已输出内容绝不重放"的安全线；
4. **场景四**（计划）：候选用最终请求预检，先构造再过滤；
5. **场景五**：账本让每次 dispatch 可见（已做），UI 提示说真话（计划）。

以及一条贯穿所有场景的纪律：**HALO 是协调层，不是第二套路由器**——主模型选择属于 Agent A，计费属于 Agent B，成功判定属于 Agent D，业界方案只借思想不搬架构，学习型路由明确不碰。
