# 并行准备工作区保护：改善大项目开始响应（#687 第二步）

本次在增量检查点的基础上，移除了无前置 hook 时首个模型请求必须等待完整备份的依赖。
检查点和文件基线仍按原顺序准备，并保留完整保护；模型可以同时准备上下文和输出文字。

```text
输入持久化并确认 ─┬─ 检查点备份 → 文件基线 → 保护就绪
                 └─ 上下文 / 模型请求 → 首段文字 → 工具等待保护 → 执行
```

## 保护边界与行为

- 每轮只有一个准备任务；工具、匹配的 hook 和结束收尾共享其完成状态。
  检查点 `beginTurn` 返回前仍会把备份和清单持久化，文件基线完成后才允许工具执行。
- `ToolRuntime` 在 hook、参数自定义验证和工具执行之前等待保护。为避免错误判断工具
  或插件的副作用，当前连只读工具也等待；Shell、Python、文件编辑、子 Agent、后台
  任务和插件使用同一入口。嵌套工具保留同一等待函数，子 Agent 也继承它。
- 没有匹配的 `UserPromptSubmit`、`InstructionsLoaded`、`PreModelRequest` hook 时，
  请求可立即开始。有匹配 hook 时先完成保护再执行。未知的自定义 lifecycle 实现采用
  保守等待策略。检查 hook 匹配不会执行 hook。
- 上下文压缩引擎有独立的 hook 分发入口。配置了 `PreCompact` 或 `PostCompact` hook
  时，本轮上下文流程整体先等待保护，即使本轮最终不触发压缩。该保守策略防止漏掉写入。
- 上下文结束捕获、`Stop` 等后置 hook 也不能提前写入。`SessionStart` / `Setup`
  保持原来的位置，在用户轮次接受前执行；本轮基线包含其已完成的修改。
- 模型文字可以在扫描结束前出现，但终态成功、文件产物和检查点收尾要等准备完成。
  准备失败会中止进行中的模型请求，禁止工具执行，记录失败，并清理租约。已经输出的
  文字无法撤回，因此失败状态仍会在流末尾明确发布。
- 取消和提前关闭输出流会取消准备过程、关闭模型迭代器，并等待清理完成。检查点遍历
  与文件基线启动支持协作取消；已经就绪后的失败轮次仍保留原来的不完整检查点收尾。
- 相同/重叠目录的租约继续串行保护写操作。等待租约期间模型可以先运行，但工具必须
  等到自身租约及保护均就绪。已有跨轮后台任务的不确定修改处理保持不变。

基线仍从持久化输入被确认后开始采集，并非推迟到第一次写入才备份。整个目录扫描不是
文件系统原子快照，模型现在可能在采集过程中读取上下文；外部修改仍按实际采集版本和
既有的写入前检查、恢复冲突校验处理。恢复/撤销文件格式不变，实际内容校验继续保留。

## 验证方法

专项入口为 `npm run build && npm run test:checkpoints`。新的并行准备测试使用生产
`AgentLoop`、`ToolRuntime`、真实检查点和文件扫描，通过可控 Promise 检查执行顺序，
避免依赖机器快慢设定耗时断言。覆盖：

- 首段文字早于备份完成，终态成功等待备份。
- 文件工具、Shell、Python、真实子 Agent、真实后台进程的首次写入及恢复/撤销。
- 真实 Shell hook、只读工具的 hook、模型前/结束 hook、压缩 hook 与未知分发器。
- 检查点已完成但文件基线尚未完成、两阶段失败、模型流中止、排队指导信息保留。
- 用户取消、提前关闭流、租约及 collector 清理、重叠工作区。

完整后端测试也执行。基线已有的 OpenAI token 计数 `strict` 断言失败及网络计时器
`unref` 导致的进程提前结束单独记录，不计为本次优化通过的验证。Gateway 恢复测试的
假模型已改为通过真实 Python 工具修改文件，避免在模型请求函数内部直接写工作区。

## 性能复现

```sh
node --import tsx scripts/benchmark-turn-startup.ts \
  --workspace /absolute/path/to/project --runs 7 --output /tmp/startup-after.json

node --import tsx scripts/benchmark-turn-startup.ts \
  --workspace /absolute/path/to/project --runs 7 \
  --implementation-root /tmp/step-one-baseline --output /tmp/startup-before.json
```

基线是**已包含第一步增量检查点**的实现。两者使用同一个未变化的目标目录，分别创建
目录外的临时备份 home；每组一次首次备份、六次未变化轮次，顺序执行，测量期间不跑
构建和测试，不清空系统文件缓存。临时备份自动删除。`--pre-request-hook` 可验证配置
前置 hook 时仍会等待保护。

脚本运行真实的对话、工具、hook 和文件保护链路；模型端使用固定等待 50 ms 的本地
实现，避免服务商和网络波动。记录的是生产链路中实际发生的首个 router 执行、文字事件、
保护就绪、首次工具调用及终态时间，起点是 `input_accepted`。探测工具是可能写入的
工具类型，但基准中的执行体不修改文件；脚本校验没有工作区变化且工具不早于保护就绪。
这些测量不是在线模型接口或 UI 绘制的端到端 TTFT。

## 本机测量结果

环境：2026-10-27，Apple M5、32 GiB、macOS 26.6、Node 22.23.4、arm64。
[完整采样与源文件校验和](benchmarks/turn-startup-687-macos.json)包含每轮的保护完成和工具执行顺序。
基线为第一步提交 `db1c1990`，增量检查点源文件校验和与第一步性能报告一致。
以下四组数据均在最终代码复查及测试完成后，对同一未变化目录顺序重新采集。

当前项目有 2134 个条目、2133 个受保护文件，共 22301087 字节。合成大目录沿用
第一步的生成规则，有 5,352 个文件、268,440,264 字节。对每个目标，前后扫描范围完全一致。

以下为六次未变化轮次的中位数，单位 ms：

| 指标 | 当前项目：第一步 → 第二步 | 大目录：第一步 → 第二步 |
| --- | ---: | ---: |
| 首个模型请求 | 268.21 → 0.25 | 421.54 → 0.26 |
| 首段文字事件 | 318.97 → 49.53 | 472.78 → 49.54 |
| 工作区保护就绪 | 267.83 → 275.24 | 421.11 → 412.36 |
| 首次工具执行 | 319.27 → 275.29 | 473.11 → 412.42 |
| 整轮完成 | 649.34 → 622.35 | 979.32 → 908.40 |

大目录首段文字等待减少 **89.5%**，首个请求前等待减少 **99.9%**。当前项目首段文字
等待减少 **84.5%**。准备保护本身的耗时基本相同；整轮完成时间分别减少约 **4.2%** 和
**7.2%**。这些指标不能混用，固定 50 ms 模型也不代表真实服务商响应速度。

首次备份仅各测一次，未清空系统缓存，结果为：

| 目标 / 指标 | 第一步 | 第二步 |
| --- | ---: | ---: |
| 当前项目首段文字 | 12918.46 ms | 53.35 ms |
| 当前项目保护就绪 | 12865.33 ms | 11908.16 ms |
| 大目录首段文字 | 31891.00 ms | 53.26 ms |
| 大目录保护就绪 | 31837.50 ms | 30906.96 ms |
| 大目录首次工具执行 | 31892.05 ms | 30907.27 ms |

所有第二步采样的首个请求都早于保护完成，所有前后采样的首次工具执行都晚于保护完成。
首次备份的真实 I/O 成本仍然存在。真实在线模型的首段文字时间还包含其网络及推理时间；
此优化主要节省原先排在请求前的准备等待，不提升模型本身的生成速度。Windows 和 UI
绘制的端到端性能尚未测量。存在前置写入 hook 的项目采用上述保守等待策略。

提交前复查又修复了两个异常路径：上下文准备抛错时保留原始错误，不再误报为输出流取消；
模型已完成而保护稍后失败时，将已持久化的助手消息保留在内存会话状态中。两项回归测试
均先复现失败，再验证修复。另外补测了同大小、恢复 mtime 的外部修改不能绕过恢复冲突，
以及恢复后下一轮基线、再次恢复与撤销的正确性。

构建及 TypeScript 编译通过；检查点专项 **125/125** 通过，另外的会话、metadata、
压缩快照回归 **31/31** 通过。本步共 **29** 个并行准备测试，增量检查点有 **18** 个专项测试。
完整后端套件的已知 token 计数断言及网络计时器问题单独记录在 PR 的验证结果中；不将
这些结果表述为全部测试通过。

提交前完整后端复核（`--test-concurrency 4`）：943 项，933 通过、1 个基线 token 计数断言失败、
7 个网络计时器取消、2 项跳过。默认并发时曾出现一次 ASR 的 1 秒响应超时；该文件单独
重跑 2/2 通过，降低并发的全量复核也未再出现。未修改这些无关模块。
