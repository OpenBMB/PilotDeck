# PilotDeck / StaffDeck 面向交付开发操作手册

适用对象：从通用 PilotDeck 应用基线开始承接新需求的开发者与编码代理。目标是用最小必要改动完成可验证的业务交付。本文只覆盖后端；兰台示例是新应用设计，不是已有系统迁移复盘。

配套材料：[可复制模板](delivery-templates.zh.md)、[兰台合同审查完整示例](lantay-contract-review-example.zh.md)、[当前基线说明](../sdk-application-base.zh.md)。

## 使用方法与责任边界

按步骤 0—7 推进，每一步记录产出。发现能力缺失时回到步骤 2 更新归属和方案，不允许通过假实现绕过验收。小模型一次领取一个开发任务单；完成当前增量、记录证据后再进入下一项。

| 组件 | 负责 | 不负责 |
|---|---|---|
| 应用后端 | 身份与业务鉴权、材料转换、业务幂等、业务状态、HTTP/SSE、交付规则 | 接管 Runtime 内部执行循环 |
| SDK | 应用访问 Gateway 的公开接口、事件消费、控制请求 | 成为持久化运行权威状态或执行前安全屏障 |
| Gateway / Runtime | 会话、执行、工具权限、运行注册表、原生记录与本地生命周期 | 内置客户数据源名称和交付业务规则 |
| 工具 / MCP | 有界的数据查询或业务操作、明确输入输出和错误 | 隐式接管整个应用状态 |
| Skill | 工作方法、领域指导、输出约定 | 强制权限或可靠状态机 |
| StaffDeck SOP | 已接入协议支持的流程转换、handoff/external task 语义 | 自动替代 PilotDeck 的工具、会话和持久化所有权 |

当前基线的已支持组合为 PilotDeck 执行与持久化 + StaffDeck 无状态 SOP 转换服务。SOP 定义快照和状态由 PilotDeck 宿主持久化。不能把七插槽设计目标当成所有未知实现均已可插拔；接入其他实现必须单独核实契约、绑定和一致性测试。

## 步骤 0：准备可复现的开发起点

**输入**：通用基线、项目仓库位置、交付范围。

**操作**：
1. 在目标目录执行 `git status --short --branch`、`git rev-parse HEAD`，确认实际 worktree、基线提交和未提交内容；不要清理别人的修改。
2. 检查基线是否包含所需 SDK/Gateway/Runtime 增量。当前 `sdk-application-base` 工作副本存在未提交增量，单独从分支引用创建 worktree 不会带走它们。先取得包含增量的审阅后提交，或明确记录并完整复制工作副本；不能只记录分支名。
3. 为新项目建立独立工作分支。记录 Node/pnpm 版本、安装命令、Gateway 配置、模型来源、工作目录和持久化目录。依赖安装按仓库锁文件执行，不借用其他 worktree 的绝对路径链接作为交付方案。
4. 按 [SDK 快速入口](../../packages/sdk/README.md) 跑通会话与一次最小运行，读取服务器能力描述；确认本次需要的 host provider 已配置。
5. StaffDeck 仅在需求需要显式流程时启用；参考 [组合说明](../../products/pilotdeck-staffdeck-sop/README.md)。

**产出**：基线记录、启动记录、能力清单。

**通过条件**：接手者能定位相同代码与配置，最小调用有明确结果。

**未通过**：先补依赖、基线或宿主配置；不要直接开始业务模块开发。

## 步骤 1：将需求转为验收场景

**输入**：用户原始需求。

**操作**：
1. 写一句话目标，列出调用者、输入材料、最终产物、人工介入点。
2. 区分必做、可选、不做；明确首版是否需要 StaffDeck、多轮会话、真实外部服务。
3. 用“给定—当—则”描述成功、失败、取消、重复请求和续接场景。仅选需求涉及的边界。
4. 定义完成：执行结束、流程完成和业务交付合格分别是什么。不要共用一个模糊的 success。
5. 预先选验收层级：本地确定性、真实服务联调、生产级验证。未选生产级时不将其作为默认阻塞条件。

**产出**：《需求卡》与编号验收场景。

**通过条件**：每个必做项都能对应可观察结果。

**未通过**：仅向需求方询问无法从代码或文档确定、且影响实现的业务决定；记录其它低风险假设。

## 步骤 2：评审能力边界

**输入**：需求卡和当前基线。

**操作**：
1. 每项需求拆到“一个能力 + 一个状态所有者”，不要按页面或大模块笼统分类。
2. 查公开 SDK 类型、Gateway handler、宿主 Port/配置和对应测试，确认端到端链路。文档与实现不一致时记录差异，以代码和可验证行为为依据修正文档。
3. 标记：直接复用、配置可用、缺宿主接线、缺公开接口、缺执行语义、纯业务开发。
4. 写明权威状态：业务任务/幂等在应用；运行状态在 Gateway-owned 持久化 RunRegistry；SOP 状态按当前组合由 PilotDeck 宿主保存；SDK sessionStore 只是镜像。
5. 对每个缺口记录证据位置、计划修改层和验证方式。

**产出**：《能力归属与接入决策表》。

**通过条件**：每项必做能力有归属和证据，不存在“接口名字存在所以已支持”的判断。

**未通过**：对有争议的单个能力做最小探针；不展开与交付无关的全仓审计。

## 步骤 3：选择最小接入路径

**输入**：能力差距表。

| 判断 | 选择 | 示例与检查 |
|---|---|---|
| 只改变工作方法或输出指导 | 配置 / Skill | 合同审查检查清单；强制交付条件仍由代码验证 |
| 增加独立数据源或可调用动作 | 工具 / MCP | 法规检索，明确查询参数、引用来源、超时及错误 |
| 构建业务服务并调用 Agent | SDK + 应用后端 | 上传材料、发起任务、审批、观察与取回结果 |
| 需要确定的步骤、交接与恢复 | StaffDeck SOP | 审查后等待人工复核，再进入修订或交付 |
| SDK 有方法但宿主未实现 | 配置或实现宿主 Port | browser/memory 等不能用空结果伪装可用 |
| 服务端能力存在但 SDK 未暴露 | SDK + Gateway 契约扩展 | 同步类型、handler、错误和能力声明 |
| 需要精确执行点、阻断或落盘顺序 | Runtime 模块 | 审计发送前屏障、工具执行前批准、快照时点 |

这些路径可以组合。每项改动写清“为什么现有较浅层方案不足”，不要求先实现一个已知不成立的方案。

模块新增采用独立模块 + 通用 Port + 窄生命周期接线；模块修改检查现有调用者、启用/禁用行为和协议一致性；模块删除优先评估禁用，真实删除须确认无调用依赖、既有状态如何处理和如何回退。不把供应商、客户或法务数据源名写入 Core。

远程 SDK callback 不承担执行前阻断、精确快照或发送前持久化。公开事件用于观察；强制语义在执行进程内实现。

**产出**：接入方案、改动范围、替代方案不适用理由。

**通过条件**：每一处 Core/Runtime 修改均有必要性；业务实现不会倒灌 Core。

**未通过**：缩小首版范围或明确缺口任务，不用无效 stub 宣称完成。

## 步骤 4：设计一条最小端到端闭环

**输入**：已确定的接入方案。

**操作**：
1. 画数据流：应用接收 → 材料准备 → SDK 上传 → Gateway 运行 → 工具/流程 → 原生结果 → 应用交付校验。
2. 定义业务 taskId 与 project/session/run、材料版本、流程实例的关联。业务幂等键与 runId 分开定义。
3. 接口逐项记录输入、输出、错误、超时、取消及权限要求。仅使用当前 SDK 版本，不另建旧协议分叉。
4. 远程附件先上传字节再提交引用；本机路径不能直接当作远端路径。
5. 断流先查询原 run，按持久化序号续接、去重；未知结果不能当成功，也不能自动换 runId 重执行。无法保证恢复时返回明确状态。
6. 区分断开观察连接与主动 abort。定义谁持有运行控制权和谁清理上传、桥接子进程及临时材料。
7. StaffDeck resume 按现有两阶段协议：宿主接受结果，再将返回消息经普通 PilotDeck 提交路径继续执行；应用接口应隐藏此实现细节，且不能收到 resume 就提前标记业务完成。

**产出**：数据流、接口表、状态所有权与错误表。

**通过条件**：一个正常请求能走完；失败时能知道状态归属和下一步动作。

**未通过**：先处理状态和恢复设计，再写并发或批量路径。

## 步骤 5：按纵向增量开发

**输入**：接口与数据流、验收案例。

**操作顺序**：
1. 最小闭环：一个输入 → 一次执行 → 一个可校验产物。
2. 补材料与工具：上传、转换、MCP 返回结构、来源关联。
3. 补业务控制：幂等、session lock、人工复核、交付门禁。
4. 补需要的恢复：重复请求、断流、取消、进程恢复。
5. 按已确认缺口扩 SDK/宿主/Runtime；独立提交范围内的实现与测试一起完成，持续保持最小闭环可用。
6. 更新配置和操作文档，记录本次支持的能力边界。

每个任务单限定目标、允许修改的层、依赖和验收命令。先读相关代码再改；保留已有修改；测试通过后仅因新改动或未解决问题扩大验证，不循环重跑已绿全套。

**产出**：实现、相关测试、每阶段证据。

**通过条件**：交付行为有测试覆盖，未配置 provider 返回明确不可用，禁用新模块后基础执行仍成立。

**未通过**：定位当前增量；避免把失败留给最终大联调。

## 步骤 6：按约定范围验收

**输入**：需求卡、实现、验收矩阵。

| 层次 | 必查内容 | 证据 |
|---|---|---|
| 能力 | 类型/handler/Port 接通，权限与错误语义，需求涉及的取消/重连/持久化 | 聚焦测试、协议探针、故障注入 |
| 业务 | 输入被正确使用、交付物存在且可读、流程门禁生效、引用可追溯 | 场景输入与实际产物、业务校验结果 |
| 交付 | 版本可定位、配置完整、启动及排错说明可执行 | 干净环境演练或明确注明未执行 |

测试选择随改动：仅改 MCP 测工具契约和一次应用集成；改 SDK 同测客户端与服务端；改 Runtime 生命周期加入相关失败路径和禁用回归；改共享协议再扩大到受影响消费者。

本地 mock、真实模型、真实 OCR、生产多实例是不同证据，不相互替代。RunRegistry 的文件锁测试不证明分布式所有权；接收 ACK 后断线不证明 ACK 未送达场景。最终报告为每项标注通过、失败、未执行或不适用及原因。

**产出**：验收矩阵、失败/未覆盖项、业务签收结论。

**通过条件**：约定必做项全通过，无假完成；未执行项不在约定阻塞范围。

**未通过**：失败返回对应开发步骤；依赖外部服务的项可调整范围，但须明确记录决定，不能自行变成通过。

## 步骤 7：交付与持续维护

**输入**：已验收成果。

**操作**：交付代码版本或完整工作副本说明、依赖与配置示例、启动和停机方法、API 调用示例、数据目录及备份责任、错误排查、升级与回退办法、验收证据。环境变量只给名称与占位值。

回退必须考虑持久化状态是否兼容；不能默认切换二进制即可恢复旧状态。提交、推送、发布按当前授权执行；未提交时明确指出仅分支名不足以复现。

通用改动整理回 PilotDeck/StaffDeck 对应模块；应用业务和数据源 MCP 保持独立，避免客户专用 Core fork。

**产出**：交付清单与后续维护责任。

**通过条件**：下一位开发者能复现、定位问题，并知道哪些能力仍依赖宿主或外部服务。

**未通过**：补交付材料，不以测试数量代替可用交付。
