# 兰台示例：从通用基线开发合同审查服务

这是新需求的示范设计，不是既有兰台 API 的描述，也不宣称以下流程已经实现或验收。按[主手册](pilotdeck-staffdeck-delivery-sop.zh.md)执行，使用[模板](delivery-templates.zh.md)记录实际决策。

## 0—1. 起点与需求卡

从包含通用 SDK/Gateway/Runtime 增量的可复现基线建立新项目；遵守[基线说明](../sdk-application-base.zh.md)，不能只 checkout 一个尚未包含工作副本增量的分支引用。

目标：企业法务上传合同，系统结合内部规则和法规生成审查报告；高风险结果必须经人工复核后交付。

示例首版约定：

- 输入支持文本 PDF 和 DOCX；扫描 PDF 仅在 OCR provider 配置后支持，否则明确要求补充可读材料。
- 输出包含逐项风险、材料位置、法规来源、修订建议及可下载报告。
- 支持首次提交、无新材料续问、补充材料后续问；保留材料版本关联。
- 高风险报告必须复核；拒绝进入修订，超时保持待复核，不自动交付。
- 首版保留完整草稿但仅交付一个当前批准版本；批准绑定报告版本，重新生成后旧批准失效。
- 本地确定性场景为必做；真实法规/OCR 联调依据凭据另行选择；生产级评测不属于本示例默认范围。

业务完成 = 审查运行终态符合要求 + 报告校验通过 + 必要复核通过。三者不能合并为一个模型返回字段。

## 2—3. 能力归属与最小接入决定

| 需求 | 归属和实现 | 为什么这样接入 |
|---|---|---|
| DOCX/PDF 转换、材料版本 | 兰台后端转换服务与材料表 | 属于业务输入管理，不修改 AgentLoop |
| 法规检索 | 法规 MCP | 数据源可替换，返回来源标识和检索结果 |
| 内部审查规则 | 项目 Skill + 业务配置 | 约束审查方法；不能替代程序化交付检查 |
| 审查任务与多轮运行 | 兰台后端调用 SDK | 复用 sessions/runs/uploads，不维护私有 WS 协议 |
| 人工复核流程 | StaffDeck SOP + 应用复核入口 | 明确 handoff、修订与交付步骤 |
| 执行中工具审批 | Gateway 权限机制 + SDK permissions | 执行许可与业务报告批准是两种状态 |
| 断线后查询、续接 | Gateway RunRegistry + SDK runs | 运行权威状态不能放在 Python 进程内存 |
| 长检索结果 | 原生归档与结果引用 | 完整证据保留与模型上下文长度分开处理 |
| 报告质量门禁 | 兰台后端 | Core 不理解“法务报告合格” |

首版不新增 Runtime 模块。先验证已有权限、审计、快照是否满足所选承诺。若新增“每次 provider 发送前必须持久化原始审计”的强制要求，就检查并启用本地审计 sink；缺口作为通用 Runtime 任务处理，不能在 SDK 收到事件后补写来冒充屏障。

## 4. 接口、状态与数据流

以下为新业务服务的示例接口，需由项目实现，不是现成 SDK 方法：

| 接口 | 输入 | 输出与行为 |
|---|---|---|
| POST /review-tasks | 合同、内部规则版本、可选业务幂等键 | taskId、任务状态；相同键同请求返回原任务，不同请求冲突 |
| GET /review-tasks/{id} | taskId | 业务状态、关联 run 状态、报告版本及是否可交付 |
| GET /review-tasks/{id}/events | taskId、续读游标 | 应用事件流；去重，历史缺口明确返回恢复指引 |
| POST /review-tasks/{id}/followups | 续问、可选新材料 | 关联同业务任务的新一轮运行；串行占用会话 |
| POST /review-tasks/{id}/decisions | 报告版本、批准/拒绝、意见 | 仅对当前待复核版本生效；重复相同决定不重复推进 |
| POST /review-tasks/{id}/cancel | taskId | 请求取消；查询 Runtime 终态后更新最终业务状态 |

应用保存 taskId、材料版本、报告版本、业务幂等和批准记录；关联 Gateway 的 project/session/run。事件游标镜像在应用，run 权威状态在持久化 RunRegistry。StaffDeck SOP 定义及状态使用当前 PilotDeck 宿主存储，不新建另一套争夺权威的流程状态机。

请求链路：

1. 应用鉴权并登记业务幂等，锁定会话，保存原材料及转换结果。
2. 将材料字节通过 SDK uploads 上传，完成后取得引用。必要时提供经过宿主 authorizer 授权的 trusted context；文档正文不能自行声明为可信上下文。
3. SDK 启动 run，应用记录 session/run 与材料版本关联，消费事件并更新可恢复游标。
4. Agent 依据 Skill 调用法规 MCP，生成草稿；保存法规来源和完整结果引用。
5. 应用校验草稿。高风险进入 StaffDeck handoff；低风险按流程定义进入交付检查。
6. 人工决定通过应用接口进入宿主 SOP resume，再沿普通提交路径推进。恢复提交失败时重试交接阶段，不能重复执行外部业务动作。
7. 对批准版本执行交付校验，发布可下载 artifact，并写业务完成状态。

失败规则：转换失败返回材料错误；数据源不可用不得编造引用；失去观察连接先查询原 run；`result_unknown` 进入待核实而非成功；取消尚未确认时不得提前报已取消；报告不合格保留草稿但不交付。

## 5. 分阶段任务

| 任务 | 最小产出 | 验证 |
|---|---|---|
| T1 文本合同闭环 | 一份文本合同到结构化风险草稿 | 确定性模型 fixture + 字段校验 |
| T2 材料与检索 | DOCX/PDF 转换、上传引用、法规 MCP | 转换 fixture、MCP 契约、材料来源关联 |
| T3 流程与门禁 | 高风险等待、批准交付、拒绝修订 | SOP handoff/resume、报告版本绑定 |
| T4 恢复与并发 | 业务幂等、会话串行、断流查询、取消 | 重复请求、同会话竞争、连接断开测试 |
| T5 交付 | 配置、运行说明、验收矩阵 | 全部必做场景和交付检查 |

StaffDeck 配置从现有 [staffdeck-sop profile](../../products/pilotdeck-staffdeck-sop/profiles/staffdeck-sop.yaml) 和 [operator approval 定义](../../products/pilotdeck-staffdeck-sop/sops/operator-approval.yaml) 开始核对。该示例只有基础 handoff；完整审查/修订图需按实际 SOP schema 开发并验证，不能把业务步骤名称直接当成合法节点类型。

## 6. 验收场景

下表是待执行的验收设计，所有初始状态均为未执行。

| ID | 场景 | 预期结果 | 首版证据 |
|---|---|---|---|
| A1 | 新任务上传文本合同 | 草稿引用正确材料版本，无虚构来源 | 本地 fixture |
| A2 | 无新材料续问 | 复用会话及已有材料关联，不重复上传旧材料 | 本地集成 |
| A3 | 补充材料后续问 | 新旧材料可区分，本轮产物关联实际使用版本 | 本地集成 |
| A4 | 高风险未批准 | 报告不可交付，状态为待复核 | 流程/业务测试 |
| A5 | 批准、重复批准、旧版本批准 | 当前版本只推进一次，旧版本不能授权新产物 | 流程/幂等测试 |
| A6 | 拒绝后修订 | 草稿保留，新版须重新判定及批准 | 流程测试 |
| A7 | 法规 MCP 超时 | 明确错误或未完成证据状态，不伪造检索结果 | 故障 fixture |
| A8 | 接收后断线再连接 | 查询同一 run，续读去重，不重复执行 | 持久化集成 |
| A9 | 主动取消 | 工具与流程按执行语义收尾，终态与业务状态一致 | 取消测试 |
| A10 | 同幂等键重复/冲突 | 同请求返回原任务，不同请求明确冲突 | 业务测试 |
| A11 | 扫描 PDF 无 OCR | 明确不可处理并保留材料，不产出假审查结果 | 输入边界测试 |
| A12 | 报告缺引用或文件不可读 | 交付门禁失败，run 完成不等于任务成功 | 产物校验 |

真实 OCR、真实法规供应商、多实例故障矩阵单列为可选验收，不由以上 fixture 代替。若合同审查业务明确要求这些能力，则在需求卡中升级为必做并提供环境。

## 7. 交付内容

交付应用后端、独立 MCP、项目 Skill 与 SOP 定义、配置示例、启动/恢复说明和验收矩阵。通用 SDK/Runtime 缺口修复独立整理；数据源名称、规则阈值、报告结构与批准策略留在应用配置和业务模块。项目初版可以只使用 SDK + MCP；没有明确交接流程时不为凑齐组件而引入 StaffDeck。
