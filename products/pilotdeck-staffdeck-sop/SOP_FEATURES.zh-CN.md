# SOP 功能介绍

SOP 用来把一项反复执行的工作，变成可复用、可跟踪的流程。例如，处理一批文件时，规定每个文件都要经过“读取资料、抽取字段、检查结果、生成报告”，再交给 Agent 执行。

你可以把它理解为一份能够实际运行的作业规范：人定义流程和要求，Agent 在每个步骤中理解资料、调用工具、产出结果，系统负责记录进度、安排并发和保存执行状态。

本文介绍当前 SOP v4 的使用能力。部署见 [部署文档](DEPLOYMENT.zh-CN.md)，详细配置与接口见 [后端说明](SOP_V4_BACKEND.zh-CN.md)。

## 适合什么工作

| 场景 | SOP 可以承担的工作 |
| --- | --- |
| 批量文件处理 | 对每份资料执行相同的解析、抽取、校验和汇总流程 |
| 企业尽调 | 识别企业股东，再对每名股东执行同一套调查步骤 |
| 报告生产 | 分步骤整理资料、查找依据、撰写内容，再汇总结果 |
| 人工复核 | 在指定步骤等待有权限的人确认，再继续执行 |
| 重复性运营任务 | 固定关键步骤和输出格式，减少每次重新描述流程的工作 |

SOP 适合步骤可以约定、处理对象可能变化的工作。业务工具是否可用、资料是否足够、模型判断是否准确，仍会影响结果。

## 一份流程如何运行

以“单份文件信息抽取”为例，流程可以是：

1. 读取当前文件，识别需要提取的信息。
2. 按约定字段输出结构化结果。
3. 检查字段是否完整，标记需要人工确认的问题。
4. 生成该文件的处理结果，交给后续汇总。

每一步都可以有自己的任务说明、输入、工具和模型。步骤之间可以传递结构化字段，也可以传递一段简短的交接说明。流程可以根据判断选择预先定义的下一步。

已发布的流程按固定版本使用。新建流程也可以引用已有流程的某个版本作为子流程，例如让“企业尽调”复用“股东调查”，让“股东调查”再复用“资料核验”。修改一个流程不会自动改变其他流程引用的版本。

## 一次提交一批任务

同一个 SOP 可以用于一份输入，也可以用于一整份任务列表。

例如，你可以提出：

> 按已发布的“文件抽取”流程处理这批文件，每个文件单独输出结果；根据任务情况选择并发数，完成后汇总成功和失败项。

在工具、流程和权限已经配置好的情况下，Agent 可以通过一次批量调用提交所有处理项，也可以通过执行代码工具组装这份列表。提交后立即取得任务编号，后续处理由系统持续调度，不需要把每一份文件都变成一次聊天工具调用。

每项有独立标识和执行状态。Agent 可为这次任务选择并发数；默认并发为 8，部署默认上限为 32，可由管理员调整。超过上限会明确报错。嵌套子流程也共享并发额度，等待子流程或人工回复不会持续占用执行名额。

“一次提交 1000 个文件”描述的是批量调度方式，不意味着 1000 个文件会同时运行，也不代表任意文件大小和解析方式都已经过性能验收。

## 按实际对象数量展开子任务

有些任务开始时并不知道要处理多少个对象。SOP 支持在运行到某一步时，先获得一份列表，再对列表中的每个对象执行指定子流程。

例如，企业资料中识别出三名股东：

```text
识别股东
  ├─ 股东甲 → 股东调查子流程
  ├─ 股东乙 → 股东调查子流程
  └─ 股东丙 → 股东调查子流程
全部结束 → 按原列表顺序汇总
```

这份列表可以来自 Agent 的判断，也可以来自前一步的结构化结果。Agent 在规划步骤可以选择并发数：设为 1 就是串行，大于 1 就是并行，并受并发上限约束。

每个对象独立处理。一项失败时默认继续处理其他项，全部结束后保留成功结果，并将整体标为存在失败。可以随后只重试失败项。

当前动态能力是“对运行时列表重复执行已指定的子流程”。它不允许 Agent 临时发明任意新节点、改写依赖关系或任意改变整张流程图。子流程最多嵌套 8 层，不能递归引用自己。

## 每一步接收哪些资料，可以单独决定

各节点使用独立的 Agent 会话。这样可以让处理当前文件的节点专注于当前任务，也避免把其他文件的对话不断累积到同一个上下文里。

默认输入包括原始用户问题、直接前一步的交接说明和当前处理项的文件引用；循环子任务还会收到当前列表项。需要更多资料时，可以显式选择：

| 输入 | 适合用途 |
| --- | --- |
| 原始问题或最新用户消息 | 保留任务目标或补充要求 |
| 前一步交接说明 | 传递判断、注意事项、下一步建议 |
| 已保存的结构化字段 | 传递企业名称、金额、检查结论等数据 |
| 当前循环项 | 告诉子流程正在处理哪名股东或哪个文件 |
| 文件引用或指定附件正文 | 按需读取文件，或直接提供需要的内容 |
| 完整对话历史 | 需要原始对话背景时显式提供 |

这些输入可以组合成模板。例如，“任务目标＋企业名称＋前一步发现的问题＋本次文件正文”。交接说明可以使用节点的回复，也可以由节点单独填写。

节点共享项目工作目录，但共享目录不等于每个节点都会自动读完全部文件。没有选择附件正文时，不会自动把全文塞进模型请求；需要读取资料的节点仍须配置相应输入或工具。各项生成结果按执行实例分别存放。

## 为不同步骤选择模型

每个节点可以指定模型。例如，把格式整理交给成本较低的模型，把复杂判断交给能力更强的模型。

选择顺序为“节点指定模型 → 本次运行默认模型 → 项目默认模型”。子流程内部节点自己的配置优先。系统记录实际模型和用量；模型不可用时会明确失败，不会静默换成另一个模型。

## 查看进度、处理失败与人工审批

运行后可以查询整体状态、完成/失败数量、当前节点、子任务、尝试次数、模型和错误，并逐页取得结果。事件记录支持持续订阅，断开后可从上次位置补取。

当前这些能力通过 Agent 工具、后端接口和 SDK 提供。可以让 Agent 查询进度，但尚没有专门的 SOP 可视化编排器或实时 DAG 看板。

| 情况 | 系统行为 |
| --- | --- |
| 某项业务失败 | 默认不自动重跑，允许明确选择失败项重试，成功项保留 |
| 用户取消 | 停止排队任务，并向运行中的后代传播取消；已发生的外部操作不能撤销 |
| 等待业务审批 | 保存等待状态，只有认证后与指定审批人匹配的主体能恢复对应项 |
| 服务重启 | 保存已完成结果和等待状态，继续调度可执行项 |
| 强制中断后无法确定操作结果 | 标记“结果不明”，禁止自动重放，先由人核对实际业务 |

业务审批需要部署方启用审批适配器；未配置时，含审批节点的流程会被拒绝。浏览器弹出的“是否允许调用工具”是另一类权限确认，不能代替业务审批。

## 与 KM 配合

SOP 负责安排工作，KM 负责保存和查找依据。例如，尽调节点可以先从知识库查询相关材料，打开引用核对来源，再产出结论，由后续节点汇总成报告。

这种配合需要为节点配置 KM 查询工具及可访问的知识空间；启用 SOP 不会自动把所有知识库开放给它。KM 也可以独立使用，详见 [KM 功能介绍](KM_FEATURES.zh-CN.md)。

## 开始使用前需要准备什么

由流程维护者发布 SOP 版本，明确各步骤任务、输入、输出、工具、模型及审批人；由部署人员完成模型与权限配置。使用者随后提供任务目标和资料，由 Agent 调用已发布流程，查询进度并领取结果。

当前版本支持独立部署，不要求 StaffDeck 服务。运行采用单个 PilotDeck 执行宿主，尚不包含多宿主分布式执行。流程执行成功表示按定义完成了步骤，业务结论仍应按实际要求复核。
